## 当前方案草案

以下内容是当前建议，尚未全部确认；示例命令与目录结构表达预期方案。

### 使用方式

建议采用单轮调用：运行程序时提供一段文本，模型返回完整回复后打印并退出。

```sh
go run ./cmd/johnny "你好，请简单介绍一下你自己"
```

先使用简单终端输入输出，后续由 v0.2 引入全局 `johnny` 命令，v0.6 引入 TUI。

### 工程结构

```text
Johnny-Code/
├── cmd/
│   └── johnny/
│       └── main.go
├── internal/
│   ├── config/
│   │   └── config.go
│   └── model/
│       └── client.go
├── go.mod
└── README.md
```

- `main.go`：读取输入、组织调用、输出结果，并设置退出状态。
- `config.go`：读取并检查当前模型服务所需的配置。
- `client.go`：封装当前模型服务的一次文本请求，处理响应和调用错误。
- `README.md`：说明如何配置、运行和验收当前版本。

### 配置与模型客户端

建议先通过环境变量提供凭据、模型名称、可选服务地址及必要的请求配置。具体配置项在首个服务确定后再讨论；本地 `.env` 加载作为可选方案。

客户端根据首个服务的实际 API 协议选择合适的 Go SDK 或实现方式。v0.3 再结合真实使用经验建设统一模型接口。

### 输出与错误处理

建议收到完整文本回复后一次性输出。正常结束时返回成功状态；输入、配置或请求失败时，给出清楚的错误提示并返回非零状态。

需要覆盖的基本场景包括：缺少输入、缺少必要配置、鉴权或模型配置错误、连接失败、请求超时，以及响应中没有可用文本。

## 验收方向草案

- 正常配置下发送一段文本，收到真实模型的有效回复。
- 连续独立运行两次，两次请求均能正常结束。
- 缺少输入或必要配置时，提示明确。
- 服务配置错误或网络失败时，报告错误并正常结束程序。
- 一起走读调用流程，能够说明输入、配置、请求和输出之间的关系。

最终验收标准在本版方案收敛后补充。
