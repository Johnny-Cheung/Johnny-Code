# v0.9 · MCP

**状态：暂缓（2026-10-25）。** v0.8 已确认冻结；v0.9 MCP 经调研后确认暂不进入实现。设计讨论保留，后续出现明确的外部服务、数据库或浏览器等需求时再启动。下一阶段优先上下文治理、长期记忆和 SubAgent。

[返回总体路线图](../johnny-code-roadmap.md)

## 本版目标

让 Johnny-Code 作为 **MCP Client** 连接外部 MCP Server，发现并调用其中的工具，同时把连接状态、失败原因和调用过程清楚地呈现给用户。

MCP（Model Context Protocol）使用 JSON-RPC 2.0 描述客户端与服务端的交互。v0.9 的重点是：

- 读取本地配置，启动或连接 MCP Server；
- 完成初始化握手，发现 Server 提供的工具；
- 把外部工具安全地暴露给模型；
- 调用工具并把结果带回 Agent Loop；
- 在 TUI 中展示连接状态、工具调用、错误和中断；
- 让每次外部调用都经过现有权限层，不因为接入 MCP 绕过 v0.7 的授权模型。

v0.9 不把 MCP 当作安全沙箱。MCP Server 是外部进程或远程服务，工具行为由其自身决定；Johnny-Code 只能在客户端侧控制连接、审批、超时、取消和结果展示。

## 已确认事项

- v0.8 已于 2026-10-25 确认冻结，版本 `0.8.0`，提交 `1dc59e0`。
- 按总体路线图，v0.9 的主题是 MCP。
- **v0.9 首版只做 MCP Tools。** Resources 和 Prompts 不在本版范围，留到后续版本。
- 不接 MCP 时保持现有 4 个基础执行工具加 `skill`；接入 MCP 后只在现有工具基础上追加成功发现的外部工具，不替换基础工具和 `skill`。
- 继续沿用 TUI-only 入口、现有四个执行工具、`skill` 工具、三种权限模式和 JSONL 调试记录。
- 继续原位复用根目录 `.env`，不搬动或重复模型配置。
- v0.9 仍是应用层策略，不是 OS sandbox；MCP Server 自身行为不受 Johnny-Code 的路径白名单限制。
- 每版独立文档；小步中文提交，每次提交后立即推送。

## 当前接入基础

- 工具接口固定为 `Definition()` + `Execute()`，注册表在启动时构建，Agent Loop 按工具名串行执行。
- 默认模式和只读模式对未显式授权的工具默认拒绝；接入 MCP 后需要明确的动态工具授权规则。
- 系统提示和工具定义在启动时生成；MCP 工具可能在连接完成后才出现，需要决定是否动态更新。
- TUI 已有工具进展、折叠摘要、审批面板、斜杠菜单和本地命令；MCP 状态可以复用这些展示能力。
- JSONL 记录工具调用和结果；MCP 配置中的 Token、Header 和环境变量不能写入记录。
- 现有 `internal/model` 统一消息层的工具定义可以直接承载 MCP 的 JSON Schema。

## MCP 能力范围

### 首版只做 Tools（已确认）

MCP Server 可以提供 Tools、Resources 和 Prompts。v0.9 只接入 **Tools**：

- 通过 `tools/list` 获取工具名称、描述和输入 Schema；
- 通过 `tools/call` 执行工具并读取结果；
- Resources 和 Prompts 留到后续版本，避免首版同时引入资源读取、模板参数和额外权限路径。

### 工具数量与暴露规则（草案）

不接 MCP 时，模型看到的工具保持当前数量：

```text
bash、read、edit、write、skill
```

接入 MCP 后，工具列表在现有基础上追加：

```text
mcp__<server>__<tool>
```

- 只有成功连接并完成 `tools/list` 的 Server 才贡献工具；
- 连接失败的 Server 不贡献工具，也不阻断其他 Server 和基础工具；
- 没有配置 MCP 或所有 Server 都失败时，行为与 v0.8 一致；
- 项目级和用户级同名 Server 如何处理、工具名冲突如何解决，仍待确认；
- 需要限制每个 Server 和整体的工具数量、Schema 大小和上下文预算，避免工具列表无限膨胀；
- 是否在只读模式下隐藏 MCP 工具，还是展示但拒绝调用，仍待确认。

### 传输方式

MCP 常见传输方式：

| 传输 | 特点 | 首版建议 |
| --- | --- | --- |
| stdio | 本地子进程，通过标准输入输出交换 JSON-RPC | 建议首选，最容易测试和清理 |
| Streamable HTTP | 远程 HTTP 服务，支持流式响应 | 视范围决定，建议第二阶段 |
| 旧版 HTTP+SSE | 兼容旧服务 | 暂不纳入 |

stdio 需要管理子进程生命周期、stderr、环境变量和退出清理；HTTP 需要处理鉴权、超时、重定向和网络错误。两者同时做会显著扩大 v0.9 范围。

### 连接生命周期

候选方案：

1. **启动时连接**：启动阶段并行连接所有启用的 Server，设置每个 Server 的超时；连接成功后构建工具列表，失败的 Server 继续展示错误但不阻断使用。
2. **首次使用时延迟连接**：启动更快，但模型在连接前看不到工具；需要额外的“发现/连接”步骤。
3. **混合**：启动时后台连接，连接完成后再更新工具列表；实现复杂，需要动态工具注册。

首版建议采用“启动时并行连接 + 每 Server 超时 + 失败不阻断”，先保证行为可解释，再考虑后台刷新。

### 工具发现与命名

建议把外部工具暴露为：

```text
mcp__<server>__<tool>
```

例如：

```text
mcp__filesystem__read_file
mcp__github__search_issues
```

需要处理：

- Server 名称限制为小写字母、数字、连字符和下划线；
- Tool 名称可能包含点号或其他字符，需要规范化并保留“显示名 → 原始名”的映射；
- 与内置工具或其他 Server 重名时，拒绝该工具或加后缀，不能静默覆盖；
- 工具有效负载中的 Schema 大小、工具数量和总上下文预算需要限制；
- 工具描述和结果都来自外部，必须按不可信文本展示和记录。

### 配置与发现（待确认）

建议支持两个层级：

```text
~/.johnny/mcp.json                 用户级，跨项目
<项目>/.johnny/mcp.json            项目级，当前工作目录
```

同名 Server 由项目级覆盖用户级。配置大致包含：

```json
{
  "servers": {
    "filesystem": {
      "transport": "stdio",
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/path/to/project"],
      "env": {"TOKEN": "${FILESYSTEM_TOKEN}"},
      "timeout_seconds": 30
    }
  }
}
```

待确认：

- 项目级配置文件是否进入仓库；如果进入，如何避免把 Token 写进项目配置；
- 是否需要单独的 `.johnny/mcp.local.json` 保存本地密钥；
- 是否支持 `${VAR}` 环境变量展开；
- 项目级配置启动本地命令前是否展示内容并要求信任确认；
- 配置文件变化后是重启加载，还是提供 `/mcp reload`。

### 权限与安全（待确认）

MCP 工具不是内置工具，调用可能产生真实外部副作用。建议：

- **默认模式**：每次 MCP 工具调用都进入审批，审批面板显示 Server、工具名、参数预览和来源；
- **只读模式**：默认拒绝所有 MCP 工具，除非后续明确实现可信的只读工具白名单；
- **放行模式**：直接执行，但仍保留超时、取消和输出限制；
- MCP 工具注解（如 `readOnlyHint`）只能作为展示提示，不能作为安全保证；
- 不因为 Server 声称“只读”就自动跳过审批；
- 不在 JSONL、TUI 或错误信息中输出配置里的 Token、Header 和完整环境变量；
- Server 返回的文本、资源和错误都按不可信内容处理，不能改变系统提示或权限策略。

需要决定是否允许“批准并记录”某个 Server 或工具；MCP 工具的能力边界通常无法从名称可靠判断，首版建议不提供记录，只允许本次批准。

### TUI 与记录

建议增加：

```text
/mcp                     查看 Server 连接状态、工具数量和错误
/mcp reload              重新读取配置并重连
/mcp reconnect <server>  重连单个 Server
```

- 启动时显示一行摘要：已连接 Server 数、工具数、失败数；
- 工具调用显示为 `mcp__server__tool`，审批面板显示 Server 和工具；
- Server 连接失败、初始化超时、工具调用失败分别显示原因；
- JSONL 记录 Server 名称、工具名、参数、结果/错误、耗时和连接状态，但不记录密钥；
- 工具结果仍然进入 `messages`，会持续占用上下文，沿用 v0.8 的说明和 v0.10 的治理方向。

### 错误、取消与超时

需要覆盖：

- Server 启动失败、初始化握手失败、协议版本不兼容；
- `tools/list` 返回无效 Schema 或重复工具；
- `tools/call` 超时、Server 崩溃、返回 JSON-RPC 错误或 `isError` 结果；
- 用户在审批或调用期间按 Ctrl+C；
- 子进程退出、stderr 有输出、管道关闭；
- HTTP 连接失败、非 2xx、响应不是合法 JSON-RPC；
- 会话退出时关闭所有 Server 子进程，不留下后台进程。

首版建议每次工具调用独立超时，取消时尽量发送 MCP 取消通知，并确保本地子进程被清理。

## 暂缓决定（2026-10-25）

- 用户确认 v0.9 MCP **暂缓**，当前不进入实现，设计文档保留为 backlog。
- 原因：MCP 的协议连接、配置信任、工具权限、输出治理、生命周期和管理界面复杂度较高；当前日常使用频率低，投入产出比不理想。
- 参考本机 Pi 1.2.0 的实现：Pi 使用独立的 `@earendil-works/pi-mcp` 客户端包，支持 stdio、Streamable HTTP、OAuth 和 Resources；默认通过 codemode/deferred 暴露避免工具列表膨胀；另有项目信任、`/mcp` 管理界面、CLI、输出截断和重连机制。完整 MCP 不是一个小切片。
- 暂缓不等于放弃。后续出现明确的外部服务、数据库、浏览器或内部系统需求时，可以基于本文件重新评估 MCP-lite 或完整实现。
- 下一阶段优先级：**v0.10 上下文治理 → v0.11 长期记忆 → v0.12 SubAgent**。上下文治理也会为未来 MCP 的工具暴露、输出限制和历史压缩打基础。

## 与前后版本的边界

- **v0.7：** 权限层负责审批、路径和命令策略；v0.9 只接入 MCP 工具，不改变既有策略。
- **v0.8：** Skill 是本地任务指导；MCP 是外部工具和资源。二者不互相替代。
- **v0.9：** 负责 MCP Client、配置、连接、工具发现、调用、状态和错误。
- **v0.10：** 负责上下文预算和工具输出治理；v0.9 只做必要的数量/大小上限。
- **v0.11：** 长期记忆；v0.9 不保存 MCP 工具结果到跨会话记忆。
- **v0.12：** SubAgent；v0.9 不引入子代理并行调用 MCP。

## 建议验收场景（草案）

1. **stdio 连接**：配置一个本地 MCP Server，启动后完成握手，`/mcp` 显示已连接和工具数量。
2. **工具发现**：模型能看到 `mcp__server__tool` 工具，Schema 和描述正确；内置工具不受影响。
3. **工具调用**：模型调用外部工具，默认模式展示审批；允许后执行并把结果带回模型。
4. **拒绝与取消**：拒绝时 Server 不执行工具；审批或调用中 Ctrl+C 能停止并清理。
5. **失败隔离**：一个 Server 启动失败或超时，不阻断其他 Server 和内置工具；错误清楚可见。
6. **协议错误**：非法 JSON、未知方法、重复工具、Schema 无效时返回明确错误，不崩溃。
7. **权限边界**：只读模式拒绝 MCP 工具；放行模式不逐次审批；默认模式不允许记录任意 MCP 工具。
8. **敏感信息**：配置文件中的 Token/Header 不出现在 TUI、JSONL 或错误信息中。
9. **生命周期**：退出会话后没有残留子进程；重连后工具列表更新。
10. **多 Server**：同名工具冲突、项目级覆盖用户级、Server 名称规范化符合约定。
