## 本版目标

通过 Johnny-Code 自己的模型调用接口，屏蔽首批模型服务的协议差异，让后续工具系统、Agent Loop 和 TUI 可以使用统一的消息、流式事件与结果。

## 已有基础与约束

- 项目使用 Go；v0.1 已跑通模型流式调用，v0.2 已通过用户验收。
- 当前 `internal/model/client.go` 中的 `Stream(ctx, cfg, prompt, output)` 同时负责创建 Anthropic 客户端、构造请求、解析流式事件、判断完成状态和输出终端正文。
- 当前模型来自中转站，模型标识为 DeepSeek-V4.1-Flash，实际请求使用 Anthropic Messages 协议与 Bearer 认证。模型品牌和调用协议是两个不同的维度。
- 继续原位复用现有 `.env`、环境变量优先级与全局 `johnny` 入口；本版讨论不要求用户迁移或重新填写已有效的配置。
- 本版方案确认后再开始代码实现。

## 建议的分层

```text
CLI（后续也包括 Agent Loop、TUI）
  ↓ 统一请求、流式事件、完整结果、错误
Johnny-Code 模型接口
  ↓ 根据配置选择
Anthropic Messages 适配器 / OpenAI Responses 适配器 / 按需加入的 Chat Completions 适配器
  ↓
中转站或模型服务
```

上层不依赖供应商 SDK 类型。适配器负责请求与返回值的转换、流式解析和协议错误处理；CLI 负责将正文片段写到终端、补换行、显示提示和决定进程退出码。

建议通过统一请求、事件回调和最终结果表达一次调用。回调可以返回错误，以便输出失败时停止请求；取消沿用 Go 的 `context.Context`。具体接口签名在范围确认后细化。

## 建议统一的内容

| 内容 | 初步建议 | 用途 |
| --- | --- | --- |
| 请求 | 系统指令、有顺序的消息列表、模型标识和输出 token 上限 | 上层可以提交完整消息，而不限于一个 prompt 字符串 |
| 流式事件 | 文本增量；工具调用相关事件随最小工具契约一起定义 | CLI 即时显示正文，后续 TUI 与 Agent Loop 消费相同的事件 |
| 完整结果 | assistant 消息、结束原因、服务实际返回的 token 用量 | 流式展示结束后，仍能拿到可用于后续调用的结构化结果 |
| 错误 | 认证、限流、服务异常、网络或协议错误；保留取消与超时语义 | 上层可以根据错误类型处理，避免依赖供应商错误字符串 |
| 能力差异 | 对尚未支持的请求明确报错，保留必要的协议差异 | 避免静默丢弃参数，或仅凭模型品牌推断能力 |

系统指令在不同协议中的位置不同，由适配器转换。统一消息列表并不意味着本版自动增加多轮交互或保存会话历史。

完整结果中的正文应与流式输出对应，终端补出的换行不写入模型消息。用量字段区分“服务未提供”和“明确返回 0”，本版不据此推算费用。

结束原因需要区分正常结束、请求调用工具、达到输出上限以及其他中断。工具调用属于模型的结构化输出，不能沿用当前纯文本逻辑将其直接视为异常；当前 CLI 对截断、空正文和调用失败的提示行为仍需有相应处理。

## 协议选择与首批范围建议

用户提出：多数拟使用的非 GPT 模型可以通过 Anthropic 兼容接口接入，GPT 使用 OpenAI 协议，并希望参考 pi agent。

这可以作为当前服务的优先选择策略；模型品牌与实际端点协议仍需分别配置。兼容接口可能由模型厂商提供，也可能由中转站转换，具体支持范围需要以实际端点为准。例如，DeepSeek 官方提供 Anthropic 兼容接口；Gemini 官方文档则说明 OpenAI 兼容接口，并建议新接入优先使用 Gemini 原生 API。这些资料不能推出所有非 GPT 服务都支持相同的 Anthropic 功能。

结合官方资料，修订初步建议为：

1. **Anthropic Messages**：作为当前默认，迁移已验证的调用；其他模型在实际服务支持该协议时复用此适配器。
2. **OpenAI Responses**：作为 GPT 接入的优先方案，符合 OpenAI 对新项目的推荐，适合后续 reasoning 与工具调用。
3. **OpenAI Chat Completions**：作为兼容接入选项；是否纳入 v0.3，根据拟用中转站的支持情况决定。仅提供 Chat Completions 的服务不能由 Responses 适配器直接调用。

上一轮首批推荐为 Messages 与 Chat Completions；本轮根据 OpenAI 官方指南调整优先级，最终范围仍待用户确认。具体端点支持情况也尚未核实，不据模型名称自动选择协议、不在请求失败后静默切换协议。

供应商 SDK 留在适配器内部，选型和具体调用方式在范围确认后核对。Responses 可以使用 `store: false` 并由客户端自行传递历史；接入它不要求改为服务端管理会话。多轮调用时需要保留相关 output items，包括服务要求重放的 reasoning 数据，不能仅保留可见正文。

建议增加一个可选的协议选择配置，字段名称待讨论；缺省使用当前 Anthropic Messages，以便已有配置继续生效。现有 Key、Base URL 和模型名继续复用，每次运行仍选择一个服务。接口路径按协议处理，配置校验需要随协议调整。

用户尚未确认最终首批范围，也尚未提供第二种协议的真实服务配置。本地模拟协议测试与真实服务验收应分别记录。

## pi-ai 参考与取舍

本轮查阅 pi agent 的模型层 `packages/ai`。原 `badlogic/pi-mono` 仓库已重定向到 `earendil-works/pi`，研究快照为 `1402973a9dbe8c627341e04c9744c54953e285ca`。以下为源码观察，与 Johnny-Code 的实现决策区分记录。

### pi 的实际划分

| 概念 | pi 中的职责 | 对本项目的启发 |
| --- | --- | --- |
| API | 线上协议实现，例如 `anthropic-messages`、`openai-responses`、`openai-completions`；最后一种对应 Chat Completions | 协议适配独立于模型品牌 |
| Provider | 管理服务端点、鉴权、模型目录和调用路由；可按模型接入多种 API | 同一个中转站可以同时提供 Anthropic 与 OpenAI 两类接口 |
| Model | 数据对象，包含模型 ID、所属 provider、使用的 API，以及能力与限制等信息 | 请求应使用明确配置的模型与协议，不按名称前缀猜测 |

pi 还实现了 Google 等其他协议，并未将所有非 GPT 模型转换为 Anthropic。当前项目可以按实际服务选用两类主力协议，同时保持接口可扩展。

### 值得借鉴的接口边界

- **统一内容块与事件。** assistant 消息由 text、thinking、toolCall 等块组成；流式事件区分块的开始、增量、结束和整轮完成，包含内容位置标识。工具参数的增量不等于完整、有效的调用参数。
- **增量展示与完整结果并存。** pi 的流既提供增量事件，也提供最终 assistant 消息；事件使用中的 partial 对象会变化，不能误当作不可变的历史快照。Go 实现应明确事件和返回结果的所有权，具体采用回调还是流对象仍待讨论。
- **保留来源与必要的协议数据。** pi 在 assistant 消息中记录 api/provider/model；同一模型续接时可以重放所需的思考签名或加密 reasoning 数据。切换模型时另做转换，处理不兼容的思考数据和工具调用 ID，并同步工具结果的关联 ID。
- **模型层与循环分开。** pi-ai 提供模型消息与调用能力，agent 层使用它组织循环。这与 Johnny-Code 的 v0.3、v0.4、v0.5 分版建设相符。

这些观察提示：统一结构需要容纳后续调用所需的信息，不能只保存屏幕上的正文，也不能原样跨服务重放全部供应商数据。本版仍是单轮命令；记录来源和保留必要数据属于接口基础，完整的跨模型历史转换尚未列入已确认范围。

### 控制本版规模

建议借鉴协议/服务/模型的边界、内容块、流式事件、最终结果及消息来源。pi 的完整模型目录、价格计算、OAuth、广泛的兼容开关和其他高级能力不作为 v0.3 的默认实现范围。当前只有一组服务配置时，也不必为了三层概念立即建设复杂的 provider 注册与模型目录系统。

## 与工具系统的边界建议

建议本版定义并验证最小的工具调用与结果消息契约，包括调用 ID、工具名、JSON 参数、结果及错误标记，并由适配器完成协议转换。流式参数片段尚未收齐时不能作为完整工具调用使用。

此处只解决模型如何表达工具请求、上层如何将结果传回模型。工具的定义管理、注册和执行属于 v0.4；根据结果继续调用模型的循环属于 v0.5。具体消息结构、事件粒度和本版验证深度仍待讨论确认。

## 候选验收场景

- 保留原有 `.env`，重新安装后仍能使用当前服务完成单轮流式问答。
- 上层通过同一个接口调用已纳入范围的协议适配器，不包含供应商 SDK 类型或按协议解析事件的逻辑。
- 模拟服务验证系统指令、有序消息、流式正文、完整结果、结束原因和用量映射。
- 最小工具消息契约确定后，使用模拟响应验证工具调用参数收集、调用 ID 关联和工具结果回传格式。
- 流式输出失败、取消、超时、鉴权失败、服务错误和提前断流能明确报告；错误不回显凭据或原始敏感载荷。
- 全局命令、帮助与版本查询、跨目录配置加载和单轮交互继续正常。
- 第二种协议具备真实服务条件后补充真实调用验收；缺少条件时明确记录验证范围。
