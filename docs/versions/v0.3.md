# v0.3 · 统一模型接口

**状态：讨论方案已汇总，尚未开始实现。下述内容整理当前方案方向，剩余待定项单独列出，不代表已经完成实现或验收。**

## 方案总结

### 目标与交付

v0.3 建立 Johnny-Code 自己的统一模型接口，让上层以相同的请求、事件与结果调用不同协议的模型服务。将现有模型请求、流式解析和终端显示的职责拆开，为后续工具系统、Agent Loop 和 TUI 提供基础。

本版完成后的直接成果是：现有 `johnny` 单轮流式问答通过统一接口运行，配置选择对应适配器，上层代码不依赖供应商 SDK 类型。

### 协议与配置

- 以 **Anthropic Messages** 和 **OpenAI Responses** 为首批主力协议的方案方向；当前服务继续默认使用 Anthropic Messages，GPT 优先考虑 Responses。
- **OpenAI Chat Completions** 作为按实际服务需要加入的兼容协议，本版是否实现仍待确定。
- 协议由配置明确指定，不根据模型品牌或名称自动推断。同一个中转站可为不同模型提供不同协议。
- 继续原位使用已有 `.env` 及环境变量优先级，现有 Key、Base URL 和模型名无需迁移或重填。新增可选协议字段，缺省保持当前行为；具体字段名与取值在实现前确定。
- API 表示协议，Provider 表示服务，Model 表示具体模型。借鉴 pi 的概念边界，当前以一组服务配置创建客户端，不引入完整的模型目录与注册系统。

### 核心接口与数据

统一入口采用以下草案：

```go
type Client interface {
    Stream(ctx context.Context, req Request, emit func(Event) error) (Response, error)
}
```

- `Request`：模型名、系统指令、有序消息列表、本次可用工具定义、输出 token 上限。
- `Message`：角色、有序内容块，以及 assistant 消息的协议、服务和模型来源。系统指令独立放在请求中。
- 内容块：`text`、`thinking`、`tool_call`、`tool_result`；工具调用与结果通过调用 ID 关联，必要的签名或加密 reasoning 数据随完整消息保留。
- `Event`：`block_start`、`block_delta`、`block_end`，按块索引关联。增量用于即时展示，最终结果返回完整 assistant 消息。
- `Response`：完整消息、结束原因与可获得的 token 用量；用量未知与 0 分别表达。

### 调用、错误与显示

- 同步、顺序触发回调，回调返回错误即停止请求；取消和超时通过 `context.Context` 传递，保留错误可识别性。应用层继续设置 5 分钟时限和当前默认输出上限。
- 区分正常完成、请求工具调用、达到输出上限及拒绝等结果状态；请求或协议失败返回错误。失败时已显示的片段可以保留，但部分结果不能当作成功回复续接。
- 工具参数收齐、整轮成功返回且结束状态允许后，才能交给后续工具层；不执行流式参数片段。
- 模型层负责协议转换和结构化结果。CLI 负责正文显示、提示、补换行与退出状态；当前继续只显示正文、处理一个问题后退出。
- 不支持的请求能力要明确报告，错误不回显凭据或原始敏感载荷。

### 版本边界与验收

v0.3 覆盖工具定义和工具消息的协议表达及转换；工具注册和执行在 v0.4 完成，自动继续调用的循环在 v0.5 完成。多轮 CLI、持久会话、完整跨模型历史转换、模型价目表和广泛兼容开关不作为本版默认范围。

验收重点：两个主力适配器通过同一接口工作；系统指令、消息顺序、块级事件、完整结果、结束原因和用量映射正确；工具消息可以往返转换；错误、取消和截断可判断；当前全局命令与配置行为继续正常。

自动测试使用模拟服务。真实服务验收优先复用当前 Anthropic 端点；OpenAI 端点的真实验证取决于实际服务条件，未验证部分需要明确记录。

### 实现前剩余待定项

1. 实际 OpenAI 服务支持 Responses 还是仅支持 Chat Completions，以及后者是否纳入 v0.3。
2. 新增协议配置字段的名称和取值。
3. 具体 Go 类型、错误分类和协议续接数据的内部表示；这些按上述契约细化，不扩展到其他版本职责。

## 本版目标

通过 Johnny-Code 自己的模型调用接口，屏蔽首批模型服务的协议差异，让后续工具系统、Agent Loop 和 TUI 可以使用统一的消息、流式事件与结果。

## 已有基础与约束

- 项目使用 Go；v0.1 已跑通模型流式调用，v0.2 已通过用户验收。
- 当前 `internal/model/client.go` 中的 `Stream(ctx, cfg, prompt, output)` 同时负责创建 Anthropic 客户端、构造请求、解析流式事件、判断完成状态和输出终端正文。
- 当前模型来自中转站，模型标识为 DeepSeek-V4.1-Flash，实际请求使用 Anthropic Messages 协议与 Bearer 认证。模型品牌和调用协议是两个不同的维度。
- 继续原位复用现有 `.env`、环境变量优先级与全局 `johnny` 入口；本版讨论不要求用户迁移或重新填写已有效的配置。
- 本版方案确认后再开始代码实现。

## 建议的分层

```text
CLI（后续也包括 Agent Loop、TUI）
  ↓ 统一请求、流式事件、完整结果、错误
Johnny-Code 模型接口
  ↓ 根据配置选择
Anthropic Messages 适配器 / OpenAI Responses 适配器 / 按需加入的 Chat Completions 适配器
  ↓
中转站或模型服务
```

上层不依赖供应商 SDK 类型。适配器负责请求与返回值的转换、流式解析和协议错误处理；CLI 负责将正文片段写到终端、补换行、显示提示和决定进程退出码。

建议通过统一请求、事件回调和最终结果表达一次调用。回调可以返回错误，以便输出失败时停止请求；取消沿用 Go 的 `context.Context`。具体接口与消息设计见后文草案，尚待讨论确认。

## 建议统一的内容

| 内容 | 初步建议 | 用途 |
| --- | --- | --- |
| 请求 | 系统指令、有顺序的消息列表、模型标识和输出 token 上限 | 上层可以提交完整消息，而不限于一个 prompt 字符串 |
| 流式事件 | 文本增量；工具调用相关事件随最小工具契约一起定义 | CLI 即时显示正文，后续 TUI 与 Agent Loop 消费相同的事件 |
| 完整结果 | assistant 消息、结束原因、服务实际返回的 token 用量 | 流式展示结束后，仍能拿到可用于后续调用的结构化结果 |
| 错误 | 认证、限流、服务异常、网络或协议错误；保留取消与超时语义 | 上层可以根据错误类型处理，避免依赖供应商错误字符串 |
| 能力差异 | 对尚未支持的请求明确报错，保留必要的协议差异 | 避免静默丢弃参数，或仅凭模型品牌推断能力 |

系统指令在不同协议中的位置不同，由适配器转换。统一消息列表并不意味着本版自动增加多轮交互或保存会话历史。

完整结果中的正文应与流式输出对应，终端补出的换行不写入模型消息。用量字段区分“服务未提供”和“明确返回 0”，本版不据此推算费用。

结束原因需要区分正常结束、请求调用工具、达到输出上限以及其他中断。工具调用属于模型的结构化输出，不能沿用当前纯文本逻辑将其直接视为异常；当前 CLI 对截断、空正文和调用失败的提示行为仍需有相应处理。

## 协议选择与首批范围建议

用户提出：多数拟使用的非 GPT 模型可以通过 Anthropic 兼容接口接入，GPT 使用 OpenAI 协议，并希望参考 pi agent。

这可以作为当前服务的优先选择策略；模型品牌与实际端点协议仍需分别配置。兼容接口可能由模型厂商提供，也可能由中转站转换，具体支持范围需要以实际端点为准。例如，DeepSeek 官方提供 Anthropic 兼容接口；Gemini 官方文档则说明 OpenAI 兼容接口，并建议新接入优先使用 Gemini 原生 API。这些资料不能推出所有非 GPT 服务都支持相同的 Anthropic 功能。

结合官方资料，修订初步建议为：

1. **Anthropic Messages**：作为当前默认，迁移已验证的调用；其他模型在实际服务支持该协议时复用此适配器。
2. **OpenAI Responses**：作为 GPT 接入的优先方案，符合 OpenAI 对新项目的推荐，适合后续 reasoning 与工具调用。
3. **OpenAI Chat Completions**：作为兼容接入选项；是否纳入 v0.3，根据拟用中转站的支持情况决定。仅提供 Chat Completions 的服务不能由 Responses 适配器直接调用。

上一轮首批推荐为 Messages 与 Chat Completions；本轮根据 OpenAI 官方指南调整优先级，最终范围仍待用户确认。具体端点支持情况也尚未核实，不据模型名称自动选择协议、不在请求失败后静默切换协议。

供应商 SDK 留在适配器内部，选型和具体调用方式在范围确认后核对。Responses 可以使用 `store: false` 并由客户端自行传递历史；接入它不要求改为服务端管理会话。多轮调用时需要保留相关 output items，包括服务要求重放的 reasoning 数据，不能仅保留可见正文。

建议增加一个可选的协议选择配置，字段名称待讨论；缺省使用当前 Anthropic Messages，以便已有配置继续生效。现有 Key、Base URL 和模型名继续复用，每次运行仍选择一个服务。接口路径按协议处理，配置校验需要随协议调整。

用户尚未确认最终首批范围，也尚未提供第二种协议的真实服务配置。本地模拟协议测试与真实服务验收应分别记录。

## pi-ai 参考与取舍

本轮查阅 pi agent 的模型层 `packages/ai`。原 `badlogic/pi-mono` 仓库已重定向到 `earendil-works/pi`，研究快照为 `1402973a9dbe8c627341e04c9744c54953e285ca`。以下为源码观察，与 Johnny-Code 的实现决策区分记录。

### pi 的实际划分

| 概念 | pi 中的职责 | 对本项目的启发 |
| --- | --- | --- |
| API | 线上协议实现，例如 `anthropic-messages`、`openai-responses`、`openai-completions`；最后一种对应 Chat Completions | 协议适配独立于模型品牌 |
| Provider | 管理服务端点、鉴权、模型目录和调用路由；可按模型接入多种 API | 同一个中转站可以同时提供 Anthropic 与 OpenAI 两类接口 |
| Model | 数据对象，包含模型 ID、所属 provider、使用的 API，以及能力与限制等信息 | 请求应使用明确配置的模型与协议，不按名称前缀猜测 |

pi 还实现了 Google 等其他协议，并未将所有非 GPT 模型转换为 Anthropic。当前项目可以按实际服务选用两类主力协议，同时保持接口可扩展。

### 值得借鉴的接口边界

- **统一内容块与事件。** assistant 消息由 text、thinking、toolCall 等块组成；流式事件区分块的开始、增量、结束和整轮完成，包含内容位置标识。工具参数的增量不等于完整、有效的调用参数。
- **增量展示与完整结果并存。** pi 的流既提供增量事件，也提供最终 assistant 消息；事件使用中的 partial 对象会变化，不能误当作不可变的历史快照。Go 实现应明确事件和返回结果的所有权，具体采用回调还是流对象仍待讨论。
- **保留来源与必要的协议数据。** pi 在 assistant 消息中记录 api/provider/model；同一模型续接时可以重放所需的思考签名或加密 reasoning 数据。切换模型时另做转换，处理不兼容的思考数据和工具调用 ID，并同步工具结果的关联 ID。
- **模型层与循环分开。** pi-ai 提供模型消息与调用能力，agent 层使用它组织循环。这与 Johnny-Code 的 v0.3、v0.4、v0.5 分版建设相符。

这些观察提示：统一结构需要容纳后续调用所需的信息，不能只保存屏幕上的正文，也不能原样跨服务重放全部供应商数据。本版仍是单轮命令；记录来源和保留必要数据属于接口基础，完整的跨模型历史转换尚未列入已确认范围。

### 控制本版规模

建议借鉴协议/服务/模型的边界、内容块、流式事件、最终结果及消息来源。pi 的完整模型目录、价格计算、OAuth、广泛的兼容开关和其他高级能力不作为 v0.3 的默认实现范围。当前只有一组服务配置时，也不必为了三层概念立即建设复杂的 provider 注册与模型目录系统。

## 统一消息与 Go 接口草案

本节将前述方向具体化，仍为待讨论的设计草案，尚未授权代码实现。

### 一次调用的入口

建议使用一个小接口，协议、服务端点和鉴权在创建客户端时确定，模型标识放在请求中：

```go
type Client interface {
    Stream(ctx context.Context, req Request, emit func(Event) error) (Response, error)
}

type Request struct {
    Model           string
    System          string
    Messages        []Message
    Tools           []ToolDefinition
    MaxOutputTokens int
}

type Response struct {
    Message    Message
    StopReason StopReason
    Usage      Usage
}
```

这段代码展示核心契约，所引用的消息、事件、工具和用量类型见下文；具体字段与校验在设计确认后落地。

配置加载层将已有配置转换为模型客户端的构造参数。模型层接收明确参数，不负责查找或读取 `.env`。Provider 的完整模型目录与注册机制可随需求增加；当前无需为了创建一个客户端引入这套机制。

`Messages` 接收调用方传入的有序历史。`System` 独立表示系统指令，适配器转换为协议要求的形式。当前 CLI 仍只构造一条用户消息；支持消息列表不代表本版新增多轮交互。

`Tools` 表达本次允许模型请求的工具，包括名称、描述和 JSON 输入 schema；本版的协议契约需要能传送它，注册、查找和执行由 v0.4 建设。

### 消息与内容块

建议 `Message` 以 `Role`、有序的 `Content` 和必要的来源信息组成。角色先覆盖 `user`、`assistant` 和 `tool`；系统指令通过请求的 `System` 表达。

| 内容块 | 关键数据 | 作用 |
| --- | --- | --- |
| text | 正文 | 用户输入、模型回答和文本工具输出 |
| thinking | 可用的思考文本及续接所需的协议数据 | 保留模型调用所需信息；当前 CLI 继续只显示正文 |
| tool_call | 调用 ID、工具名、JSON 参数 | 表达模型请求的工具调用 |
| tool_result | 对应调用 ID、结果内容、是否为工具执行错误 | 将工具结果关联回原调用 |

角色与内容块的组合需要校验。例如，assistant 可以同时包含正文和多个工具调用，tool 消息承载工具结果，不能把一段正文中的 JSON 文本自动当作工具调用。

Go 中建议用带类型标记的结构体表达内容块，内部使用具体的文本、思考、工具调用或工具结果字段，并校验与类型对应的有效载荷。工具参数建议使用 `json.RawMessage` 保留完整 JSON，再验证其为合法对象；参数是否符合工具 schema、是否可以执行，交由工具层处理。

assistant 消息记录协议、服务标识和模型标识。思考签名、加密 reasoning item 等适配器专用数据使用带来源标记的不透明数据保存，明确归属和顺序，避免进入显示正文或错误日志。具体表示形式需结合首批协议的 SDK 返回值确定，不向上层暴露 SDK 对象。

跨模型切换时如何转换这些历史数据仍需单独设计，本版首先保证来源明确、同一服务续接需要的信息不丢失。

### 流式事件

建议最小事件契约包括三类，并使用稳定的 `BlockIndex` 关联同一内容块：

| 事件 | 语义 |
| --- | --- |
| block_start | 开始一个内容块，说明块类型；仅包含当时已经确定的信息 |
| block_delta | 该块新产生的正文、思考文本或工具参数片段 |
| block_end | 该块已经收齐，提供完整块数据；工具 ID、名称和参数在此校验是否完整 |

同一块遵循开始、增量、结束的顺序。适配器负责将各协议的事件转换成这一契约；不同块的事件可以交错，上层按索引关联。工具参数片段仅用于展示或组装，不能提前执行；完整工具调用也须等整轮成功返回并确认结束原因后再交给后续工具层。

最终 assistant 消息按块顺序组装，与事件内容一致。事件携带当前片段或已完成块的独立数据，不把持续变化的整条消息引用交给调用方留存。适配器专用的续接数据保存在完整结果中。

整轮完成由 `Stream` 的返回值表达，失败由返回的 `error` 表达；初版不再另设重复的整轮 done/error 事件。`block_end` 仅表示该块结束，不能据此判断整个请求成功。

### 回调、取消与失败

- 回调在 `Stream` 调用的同一 goroutine 中按事件顺序执行；调用期间适配器不并发触发回调，返回后不再触发。
- 回调处理速度形成自然背压，调用方应及时消费；未来 TUI 可以在应用层桥接到自己的事件系统。
- 回调返回错误时停止本次请求，关闭流，并保留错误链，使上层能识别原始输出错误。
- `emit == nil` 表示调用方只需要完整结果；底层仍按流式方式请求并组装结果。
- 请求的取消和时限由 `context.Context` 控制。应用层继续设置当前 5 分钟时限，适配器保留 `context.Canceled` 与 `context.DeadlineExceeded` 的可识别性。
- 请求失败时返回已收集的部分 `Response` 和非空错误。部分结果可以用于展示和诊断，不能标记为成功回复或自动作为完整历史续接。

### 完整结果与上层处理

结束原因首先覆盖正常完成、请求工具调用、达到输出上限、模型拒绝；无法解释的结束状态要明确报告协议错误。用量使用可选字段，区分缺失与 0，至少记录实际可获得的输入、输出 token；缓存与推理分项在适配时明确统计口径，避免重复计数。

正常结果、达到上限与工具调用是模型层的不同结果状态，由上层结合用途处理。例如，当前文本 CLI 对达到输出上限继续提示回复可能不完整，未来 Agent Loop 在收到完整工具调用后进入工具执行阶段。

CLI 的典型处理过程为：

```text
现有配置 → 创建协议客户端 → 构造一条 user 消息
  → Stream：收到 text 增量就写 stdout
  → 返回 Response/error：检查结束状态，补终端换行，决定退出码
```

完整结果中的正文不包含终端额外补出的换行；CLI 不应在收到最终结果后再次打印已经流式显示过的正文。

## 与工具系统的边界建议

建议本版定义并验证最小的工具调用与结果消息契约，包括调用 ID、工具名、JSON 参数、结果及错误标记，并由适配器完成协议转换。流式参数片段尚未收齐时不能作为完整工具调用使用。

此处只解决模型如何表达工具请求、上层如何将结果传回模型。工具的定义管理、注册和执行属于 v0.4；根据结果继续调用模型的循环属于 v0.5。具体消息结构、事件粒度和本版验证深度仍待讨论确认。

## 候选验收场景

- 保留原有 `.env`，重新安装后仍能使用当前服务完成单轮流式问答。
- 上层通过同一个接口调用已纳入范围的协议适配器，不包含供应商 SDK 类型或按协议解析事件的逻辑。
- 模拟服务验证系统指令、有序消息、流式正文、完整结果、结束原因和用量映射。
- 最小工具消息契约确定后，使用模拟响应验证工具调用参数收集、调用 ID 关联和工具结果回传格式。
- 流式输出失败、取消、超时、鉴权失败、服务错误和提前断流能明确报告；错误不回显凭据或原始敏感载荷。
- 全局命令、帮助与版本查询、跨目录配置加载和单轮交互继续正常。
- 第二种协议具备真实服务条件后补充真实调用验收；缺少条件时明确记录验证范围。
