## 本版目标

在已通过验收的工具系统、Agent Loop 和 TUI 之上，建立统一的工具执行授权机制：让用户知道模型要做什么、可以批准或拒绝，并在拒绝和中断下保持明确的执行结果。

## 执行前统一决策（方向已确认）

工具执行前由统一的权限层给出三种结果：允许、需要用户确认、拒绝。文件内容、模型回复、工具结果以及后续接入的 Skill 都不能自行改变权限策略。

执行顺序：

1. 解析并校验本次工具参数，确定操作对象与工作目录。
2. 按当前权限模式、文件范围和显式规则作出决策。
3. 需要确认时展示具体操作，等待用户选择；等待期间不执行工具。
4. 允许后执行；拒绝时向模型返回明确的权限结果，并记录决策。
5. 沿用现有取消、超时、工具结果回传与会话历史规则。

拒绝不能被解释成可以换一个工具执行同一项未授权操作。取消审批时也不能在后台继续执行。

## 三种权限模式（方向已确认）

权限模式采用 **只读、默认、放行**。只读用于检查和分析，默认用于日常开发，放行保留当前直接执行的体验。

以下为已确认的操作规则：

| 模式 | 普通文件读取 | 写入/编辑 | Bash | 范围外访问 |
| --- | --- | --- | --- | --- |
| 只读 | 工作目录内允许（敏感文件也允许） | 拒绝 | 仅开放白名单查询命令 | 工作目录外拒绝 |
| 默认 | 路径白名单内自动允许 | 路径白名单内自动；路径外审批 | 用户级白名单/项目前缀自动，其余审批 | 路径外审批，可批准并记录 |
| 放行 | 允许 | 允许 | 允许 | 允许 |

**三种模式和默认模式审批已实现；运行时模式切换尚未实现；按当前确认范围，v0.7 不包含 OS sandbox。**

### 只读模式

只读模式用于让 Agent 检查、分析和解释项目，禁止通过任务工具修改文件或执行有副作用的程序；程序本身的模型请求与会话日志仍按约定运行。`read` 用于读取，`write` 用于创建或覆盖文件，`edit` 用于修改文件。写入与编辑直接拒绝。

用户提出只保留现有四个工具，只读模式允许 `read` 和受限的 Bash 白名单，而不是新增查询工具或完全禁用 Bash。按这个方向实现，但白名单必须按“程序 + 参数 + 路径”检查，不能只按命令名放行。

只读模式的基本约束：

- 当前支持固定查询命令组成的简单命令、管道、`&&`/`||`/`;` 链、工作目录内虚拟 `cd` 和三种尾部安全重定向；其他重定向、命令替换、后台执行、循环、条件和脚本解释器仍拒绝。
- 不经过 shell 执行。校验通过后按直接 argv 和 OS pipe 启动程序，避免 `>`、`|`、`$()` 等 shell 语法被执行。
- 每个程序维护自己的参数白名单；未知参数、写文件参数和会执行其他程序的参数直接拒绝。
- 路径参数必须解析到允许范围；绝对路径、`..`、符号链接和工作目录外路径都要检查。
- 沿用现有超时、输出限制、取消和进程清理；命令查找失败或规则不支持时返回明确错误。
- 非白名单命令返回权限错误，模型可以改用其他查询命令；不能通过一次错误自动切换到默认或放行模式。
- 仍然执行读取范围规则；按用户选择，工作目录内 `.env`、私钥等敏感文件允许读取，不做敏感拒绝列表。

只读模式当前允许固定查询两档共 21 个命令的受限形式，使用与默认模式相同的分段器；下表保留首版讨论时的用途说明，其中 4 个命令是 2026-10-23 第一切片范围，当前完整名单和参数以“权限收口方案”为准：

| 程序 | 建议用途 | 需要限制的形式 |
| --- | --- | --- |
| `pwd` | 查看当前工作目录 | 无参数 |
| `ls` | 列目录 | 路径参数、递归和格式化选项需白名单，避免跟随范围外链接 |
| `find` | 按名称/类型查找 | 拒绝 `-exec`、`-delete`、`-fprint`、写出文件和跟随链接的形式 |
| `grep` | 搜索文件内容 | 拒绝执行外部程序、从任意文件加载模式及写出结果的选项；路径需受限 |
| `cat` | 读取文件内容 | 仅普通文件；路径范围检查，避免特殊文件阻塞 |
| `head` / `tail` | 查看文件片段 | 拒绝持续跟踪和写出文件的形式；仅普通文件 |
| `wc` | 统计行数/字节数 | 路径范围检查，仅普通文件 |

暂不建议把 `git`、`sed`、`awk`、`xargs`、脚本解释器、构建和测试命令放进用户级只读白名单。`git status` / `git diff` 可能写索引锁、调用外部 diff、读取全局配置或执行配置中的外部程序；默认模式另有一套 Git 只读子命令的项目前缀规则，见“默认模式最终模型”。

测试、构建和运行项目脚本即使用了“检查”目的，也可能创建缓存、产物或执行任意代码，不属于只读查询；需要时使用默认模式的审批，或显式选择放行模式。

白名单是工具层控制，不是操作系统沙箱。即使只允许上述程序，递归搜索仍可能读取敏感文件，程序也可能产生缓存、锁文件或通过配置执行外部程序；严格的文件写入限制仍需要沙箱。当前固定表为 21 个命令（14 纯读 + 7 逃逸口），以“权限收口方案”为准；本段其余为首版讨论记录。

## Claude Code 只读机制调研（2026-10-23）

参考官方文档：[权限模式](https://code.claude.com/docs/en/permission-modes)、[权限规则](https://code.claude.com/docs/en/permissions)、[Bash sandbox](https://code.claude.com/docs/en/sandboxing)、[工具参考](https://code.claude.com/docs/en/tools-reference)、[Agent SDK 权限](https://code.claude.com/docs/en/agent-sdk/permissions)。

### 官方机制要点

- Claude Code 没有名为“只读”的独立权限模式。最接近的是 **plan mode**：允许读取文件和运行探索性 shell 命令，在用户批准计划前阻止源代码编辑；它不是硬性只读，交互环境中仍存在绕过审批的路径。
- 官方内置一组自动允许的只读 Bash 命令，包括 `ls`、`cat`、`echo`、`pwd`、`head`、`tail`、`grep`、`find`、`wc`、`which`、`diff`、`stat`、`du`、`cd` 和只读形式的 `git`；该集合不可配置。plan mode 下这些命令自动运行，其他命令进入审批或分类器。
- 工具权限使用 `allow`、`ask`、`deny` 规则，按 deny → ask → allow 的顺序匹配。Bash 规则会拆分 `&&`、`||`、`;`、`|` 等组合命令，并检查重定向，但官方明确说明 **Bash 规则匹配的是命令文本，不是程序的安全边界**；带参数白名单的规则很脆弱，`/bin/rm`、`sh -c`、解释器和脚本都可能绕过。
- 真正的强制边界是 **Bash sandbox**：macOS 使用 Seatbelt，Linux/WSL2 使用 bubblewrap+socat，原生 Windows 不支持；它只覆盖 shell 命令及其子进程，不覆盖 Read/Edit/Write、MCP 或 hooks。没有单个“只读”总开关，需要配置文件系统 `denyWrite` 等规则；默认读取范围较宽，包含不少凭据路径，网络代理也不是完整隔离。
- SDK 的 `allowed_tools` 是自动批准列表，不是工具白名单；要移除工具应使用裸工具名的 `disallowed_tools` 或 `tools` 列表。plan mode 下编辑类调用会转给 `canUseTool`，即使 allow 规则匹配也不能自动批准。
- 在 macOS/Linux/WSL 上，Claude Code 默认不使用独立的 Glob/Grep 工具，而是通过 Bash 中的 `find`/`grep` 查询；原生 Windows 才默认提供这些工具。这说明“通过 Bash 做只读查询”本身是官方采用的路线，但它同时配合权限规则和 sandbox。

### 对四工具方案的启示

- 我们的“`read` + 受限 Bash 白名单”与 Claude Code 的内置只读命令集方向一致；但 Claude Code 官方也明确认为 Bash 规则不是安全边界。因此本项目的只读模式应描述为 **工具策略上的只读**，不能宣称为 OS 隔离。
- 如果只依靠白名单，即使不经过 shell 并逐项校验参数，仍可能存在命令自身副作用、递归读取敏感文件或平台差异；`git` 等命令尤其明显。
- 要获得硬性只读保证，只有两条可靠路线：只保留 `read`、移除 Bash，或者引入真正的 OS sandbox；后者已超出当前四工具白名单的实现范围，是否纳入 v0.7 仍需共同决定。
- Claude Code 的内置只读命令集合可以作为参考，但不需要全部照搬。首版可以保留更窄的 `pwd`、`ls`、`find`、`grep`，也可以按实际需要加入 `cat`/`head`/`tail`/`wc`；Git 是否进入首版仍建议单独确认。
- Claude Code 的 Read/Edit 路径规则和 Bash 正则/前缀规则也说明：**权限应放在程序执行前，不能只依赖系统提示或模型自觉**。本项目后续实现应保持同样的原则。

## Codex 调研（2026-10-23）

参考官方文档：[Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)、[Sandbox](https://learn.chatgpt.com/docs/sandboxing)、[Permissions](https://learn.chatgpt.com/docs/permissions)、[Rules](https://learn.chatgpt.com/docs/agent-configuration/rules)。结论对 Codex 版本敏感，本次参考 0.164 附近的官方文档与源码。

- Codex 把 **sandbox mode** 与 **approval policy** 分开：前者决定技术边界，后者决定何时询问。sandbox mode 为 `read-only`、`workspace-write`、`danger-full-access`；approval policy 当前主要是 `on-request` 和 `never`（旧的 `untrusted`、`on-failure` 已退役或弃用）。
- `read-only` 是 **OS 级 sandbox**：macOS 使用 Seatbelt，Linux/WSL2 使用 bubblewrap + seccomp，Windows 使用 MXC 或兼容方案。默认允许读整个文件系统（受 OS 用户权限限制）、禁止写普通文件、默认禁止命令联网；`/tmp` 和 `$TMPDIR` 在 read-only 下也不自动可写。
- `read-only` 下的普通命令仍可在 sandbox 内运行；`on-request` 允许模型申请越过 sandbox，经用户批准后写入或联网。更接近硬只读的组合是 `read-only + never`，但还需要没有 `allow` 型命令规则、没有其他越界工具。
- 命令规则使用 Starlark `prefix_rule`，按 argv 前缀匹配；`allow` 的语义是“直接在 sandbox 外运行，无需提示”。因此命令规则不能替代 sandbox，反而可能成为绕过只读的入口。复杂 shell 不会被可靠拆分。
- sandbox 覆盖启动的命令及其子进程，也约束通过文件系统策略执行的编辑工具；不覆盖环境变量、web search、MCP、apps、browser 等其他通道。环境变量默认继承，且不会自动过滤 `KEY`/`SECRET`/`TOKEN`。平台无法强制 sandbox 时，Codex 拒绝执行，而不是静默无沙箱运行。
- Codex 当前没有稳定的独立 Read/Glob/Grep 工具，主要用统一 shell 读取和搜索、用 `apply_patch` 编辑。它的取舍是“少工具 + 通用 shell + OS sandbox”，而不是“用命令白名单模拟只读”。

## Pi Agent 权限管理源码调研（2026-10-23）

研究对象是本地源码 `/Users/johnny/Documents/Johnny/Agent/pi`，对应 `@earendil-works/pi-coding-agent` 1.2.0、commit `00d8d0495`（`v1.2.0-25`）。参考：[CLI tools](https://pi.dev/docs/latest/cli#tools)、[Security](https://pi.dev/docs/latest/security)、[Extensions](https://pi.dev/docs/latest/extensions)、[Containerization](https://pi.dev/docs/latest/containerization)。

### 核心结论

Pi 没有内置的权限策略、逐次审批、只读模式或 OS sandbox。它提供的是几组可组合的原语，把“要不要确认、限制哪些路径、是否隔离”留给扩展和外部环境：

- **工具暴露**：`--tools`、`--exclude-tools`、`defaultTools`、`pi.setActiveTools()`。
- **执行前钩子**：`packages/agent` 的 `beforeToolCall`，在 coding-agent 中暴露为扩展的 `tool_call` 事件；可阻止执行或改写参数。
- **项目信任**：控制启动时是否加载项目内的扩展、MCP 配置、Skills 等资源，不是工具审批。
- **示例级策略**：`permission-gate.ts`、`protected-paths.ts`、`tool-override.ts`、`plan-mode`、`sandbox`、`gondolin`，都不是默认启用的内置能力。

`docs/security.md` 明确写明：工具和扩展以启动 Pi 的操作系统用户权限运行，默认不会在每次工具调用前请求批准；工作目录只影响资源发现和工具默认位置，不限制命令访问其他路径；项目信任不是工具调用边界；Pi 不自带 sandbox。README 也说明 plan mode、sub-agents 等不是内置功能。

### 1. 工具暴露不是权限边界

- 默认启用的内置工具是 `read`、`bash`、`edit`、`write`（源码中的 `DEFAULT_TOOL_NAMES`）；`grep`、`find`、`ls` 内置但默认关闭。
- CLI 文档给出的只读示例是 `pi --tools read,grep,find,ls --print "Review this project"`；SDK 也提供 `createReadOnlyTools()`，返回 `read`、`grep`、`find`、`ls`。这个组合**不含 Bash**，因此比命令白名单更接近“没有写入/执行工具”。
- `--tools` 用普通名称时替换整个选择；`--exclude-tools` 在最后按名称或通配符排除；`defaultTools` 可持久化；扩展可以在运行时调用 `pi.setActiveTools()` 改变集合。
- 这只是“把工具从模型可见集合中移除”，不是审批，也不是文件系统边界。`read`、`grep`、`find`、`ls` 都接受绝对路径并展开 `~`，可以访问工作目录外的文件；`read` 没有 `.env`、私钥等敏感文件拒绝。已加载的扩展还可以在运行时重新启用工具，所以 `--tools` 也不是对扩展的硬边界。
- 因此 Pi 的“只读”含义是“没有写入/执行工具”，不是“只能读工作目录”，也不是“不能读取敏感内容”。

### 2. `beforeToolCall` / `tool_call` 是真正的权限接入点

- `AgentLoopConfig.beforeToolCall` 在参数准备和 schema 校验之后、工具执行之前调用。返回 `{ block: true, reason?: string, terminate?: boolean }` 会阻止执行；被阻止的调用变成一条 `isError` 工具结果回传给模型，`reason` 作为文本。
- coding-agent 的 `AgentSession` 安装该钩子，把调用分发给扩展的 `tool_call` 事件。扩展可以返回 `{ block: true, reason }`，也可以原地修改 `event.input` 来改写工具参数。
- 并行工具批次会先把整批调用逐个预检（解析、校验、`beforeToolCall`）后才开始执行，因此审批按调用顺序进行；整批预检结束后，所有获准调用并发执行。顺序模式则逐个预检、执行。
- 扩展处理器按加载和注册顺序运行；`block` 会短路后续处理器。`event.input` 可变，后续处理器会看到前面的修改；官方明确说明修改后**不会重新校验 schema**。所以权限扩展的加载顺序很重要：如果它在某个改写参数的扩展之前批准，后续扩展仍可能把参数改成未授权内容。核心没有权限优先级或“最后检查”机制。
- `tool_call` 处理器抛错会向上传播，最终由 agent loop 转成错误工具结果，即失败关闭（fail-closed）；官方文档也写明 `tool_call` handler failure blocks the tool。
- 嵌套工具调用（`ctx.executeTool`）、codemode 和 MCP 工具都走同一 `tool_call` 钩子，并带 `parentToolCallId`。用户手动 `!` shell 不走 `tool_call`，而是单独的 `user_bash` 事件；完整的 Bash 权限或沙箱需要同时处理这两个入口。
- `afterToolCall` / `tool_result` 可以改写或脱敏工具结果，但它不是执行前的权限决策点。

### 3. 官方示例如何实现策略

Pi 仓库没有默认启用的权限扩展，`examples/extensions` 提供了几种参考：

- `permission-gate.ts`：只检查 Bash 命令文本的少量正则（`rm -rf`、`sudo`、`chmod/chown 777`）。交互模式用 `ctx.ui.select` 询问；`ctx.hasUI == false` 时直接阻止。它不覆盖 read/edit/write，也不是完整审批。
- `protected-paths.ts`：在 `tool_call` 中检查 `write`/`edit` 的输入路径字符串是否包含 `.env`、`.git/`、`node_modules/`，命中就阻止。它是子串匹配，不解析真实路径，不覆盖 Bash，也不限制 read。
- `tool-override.ts`：用同名工具覆盖内置 `read`，在自定义实现里记录访问日志并拒绝 `.env`、secrets、credentials、SSH/AWS/GPG 等路径。它说明扩展可以包裹或替换内置工具做访问控制；但只覆盖 read，Bash 仍可 `cat`。
- `plan-mode`：最接近只读模式，但只是示例扩展，不是内置模式。启用后通过 `setActiveTools` 去掉 `edit`/`write`，保留 `read`/`bash`/`grep`/`find`/`ls` 以及所有其他已激活工具；Bash 用 `SAFE_PATTERNS` 白名单加 `DESTRUCTIVE_PATTERNS` 黑名单过滤。
- `sandbox`：见下一节。
- `gondolin`：把内置工具路由进本地 micro-VM，宿主机工作目录挂载到 `/workspace`；其他扩展工具仍在宿主机运行。

`plan-mode` 的过滤只按整条命令字符串做正则，不解析 shell，因此官方 `isSafeCommand` 会放行一些明显有副作用或可执行任意代码的命令。用本地源码逐条验证过：

- `find . -delete`
- `find . -fprint /tmp/out.txt`
- `find . -exec python3 ...`
- `sort -o /tmp/out.txt file.txt`
- `sed -n 'w /tmp/out.txt' file.txt`
- `curl -o /tmp/out.txt https://example.com`
- `cat file.txt; python3 -c '...'`
- `git log --output=/tmp/out.txt`
- `git branch new-branch`
- `git remote add x https://example.com`

它还会保留其他 active tools，所以自定义工具或 MCP 工具仍可能在 plan mode 中写文件；切换也是运行时的 `/plan`，不是启动时不可变模式。该示例适合演示，不适合作为安全边界。

### 4. 项目信任不是工具审批

- `.pi/settings.json`、`.pi/mcp.json`、`.pi/extensions`、`.pi/skills`、`.pi/prompts`、`.pi/themes`、`.pi/SYSTEM.md`、`.pi/APPEND_SYSTEM.md` 以及项目 `.agents/skills` 等资源，加载前需要项目信任。
- 决策顺序：`--approve` / `--no-approve` 命令行覆盖优先；其次由用户级或命令行扩展处理 `project_trust` 事件；再次使用 `~/.pi/agent/trust.json` 中保存的目录决策；最后使用 `defaultProjectTrust`，默认 `ask`。非交互模式无法弹窗，`ask`/`never` 会跳过受保护的项目资源。
- `--approve` 只表示“本次信任项目本地资源”，不是批准某个工具调用，也不是权限模式。`/trust` 用于保存项目信任决策。
- `AGENTS.md`、`CLAUDE.md` 等上下文文件不受项目信任保护，仍会被读取并进入模型上下文；项目信任不能阻止提示注入。

### 5. OS sandbox 只是示例，而且 fail-open

- `examples/extensions/sandbox` 使用 `@anthropic-ai/sandbox-runtime`（macOS Seatbelt、Linux bubblewrap），配置网络 allowlist、`denyRead`、`allowWrite`、`denyWrite`。
- 它只覆盖内置 `bash` 和用户 `!` 命令（`user_bash`），不覆盖 `read`/`edit`/`write`、MCP 或其他扩展工具。Pi 进程本身仍在宿主机上，文件工具仍以宿主进程权限运行。
- 平台不支持、配置关闭、`--no-sandbox` 或初始化失败时，示例会把 `sandboxEnabled` 设为 false 并回退到普通 Bash，属于 fail-open；这适合演示，不适合作为强制边界。
- `docs/security.md` 建议真正的隔离使用整进程容器、VM、Docker Sandboxes、OpenShell 或 Gondolin 微 VM；这些方案也各有边界，例如 Gondolin 只隔离路由进去的工具，其他扩展仍在宿主机，命令还会继承宿主环境变量。
- Pi 的 Bash 默认环境是 `{...process.env}`，只移除少量 `PI_*` 变量，其他环境变量会进入子进程；没有内置的凭据变量过滤。

### 6. 对本项目的启示

- Pi 证明了“四工具 + 可组合权限钩子”可行，但它把策略留给扩展；我们的 v0.7 把只读策略放在核心 `ReadOnly` 包装中，不依赖扩展加载顺序，这是更强的默认保证。
- Pi 的 `beforeToolCall` 语义（校验后、执行前、block 变成工具错误、fail-closed）可以作为我们默认模式审批的参考。
- 不要把工具暴露、命令白名单、项目信任和 OS sandbox 混为一谈：它们分别是暴露面、应用层策略、启动资源信任和强制隔离。我们的文档要继续区分“工具策略只读”和“OS 沙箱”。
- Pi 的只读组合不含 Bash，这再次说明：如果产品要“硬只读”，最干净的是不暴露 Bash；保留 Bash 就必须承认它是策略性护栏，真正的边界要靠 sandbox。
- 如果未来接入 Skills、MCP 或扩展，权限钩子必须覆盖嵌套工具和 MCP，并且要在所有参数改写之后做最终校验（或由核心重新校验），不能照搬 Pi 的“修改后不重新校验 + 依赖扩展顺序”。
- Pi 的 Bash 默认继承完整环境变量；我们只读模式的最小环境 allowlist 是更保守的选择。

## 三家对照与对本项目的结论

| 方面 | Claude Code | Codex | Pi | Johnny-Code 四工具方案 |
| --- | --- | --- | --- | --- |
| 只读形态 | plan mode + 内置只读命令自动放行 | read-only OS sandbox + 审批策略 | 只读工具组合（无 Bash）或 plan-mode 示例白名单 | `read` + 受限 Bash 白名单 |
| 权限实现点 | 内置 allow/ask/deny 规则 + 可选 sandbox | sandbox mode + approval policy | 扩展 `tool_call` 钩子 + active tools；无内置策略 | 只读包装与默认模式审批已实现 |
| 审批 | 规则匹配 + 分类器/用户确认 | `on-request` / `never` | 示例扩展自行实现 | 三选项 TUI 审批已实现 |
| Bash | 保留；只读命令自动运行，其他审批 | 保留；在 sandbox 内运行 | 严格只读组合不含 Bash；示例模式用白名单 | 保留；白名单查询 |
| 白名单定位 | 权限提示，不是安全边界 | 审批/例外管理；`allow` 会绕过 sandbox | 示例护栏，不是安全边界 | 拟作为策略护栏 |
| 硬隔离 | 可选 Bash sandbox，仅覆盖 shell | OS sandbox，覆盖命令及子进程 | 无内置；外部 sandbox/容器 | 暂无 |

三家共同结论：

1. **命令白名单不能作为只读的安全边界。** 三家都没有把“命令前缀/正则匹配”当成隔离机制；它最多用于减少误操作、审批提示或缩小暴露面。
2. **严格只读最简单可靠的实现是不暴露 Bash。** Pi 的官方只读组合和 Claude Code 的只读工具方向都支持这一点；Codex 用 OS sandbox 保留 Bash，但 sandbox 也明确不是完整隔离。
3. **如果保留 Bash，真正的边界应来自 OS sandbox 或外层容器/VM，且不可用时必须 fail-closed。** 这不是命令白名单能替代的。
4. **审批与隔离要分开。** 允许一次越界操作后，模式就不再是硬只读；产品文案必须区分“默认不写”“工具策略不写”和“操作系统强制不写”。
5. **权限检查必须放在执行前，并覆盖所有调用路径。** Pi 的 `tool_call` 钩子已覆盖嵌套和 MCP，但参数可变且不重新校验、依赖扩展顺序；这提示我们应在最终参数上做核心校验。

对本项目的建议：

- 可以继续按用户方向实现四工具只读模式：`read` + 通过 argv 校验的查询 Bash 白名单（建议首版 `pwd`、`ls`、`find`、`grep`），不经过 shell，逐命令限制参数和路径。它是**策略性只读**，不是 OS 隔离。
- 如果产品上要把“只读”解释为硬保证，则只读模式应只暴露 `read`（或未来增加只读查询工具），把 Bash 留在默认/放行模式；或者引入 OS sandbox 后再开放 Bash。
- 不建议首版把 Git、构建、测试、解释器和任意 shell 组合放入白名单；它们会破坏“只读”的语义。
- 如果 v0.7 引入 sandbox，建议先限定 macOS/Linux，覆盖 Bash 子进程，禁止写入和网络，sandbox 不可用时拒绝 Bash；同时仍用应用层路径规则保护 `read`/`edit`/`write`，不能把 Bash sandbox 当成所有工具的隔离。
- 这些结论仍待用户选择：接受策略性只读并继续四工具白名单，还是为了硬保证采用“只读仅 read”或增加 sandbox。

### 放行模式

放行模式保留当前 v0.4～v0.6 的直接执行体验：不弹逐次确认，四个内置工具按当前能力执行。它不是操作系统沙箱，也不代表命令被限制在工作目录内；启动时应明确显示“放行模式”，避免用户误以为仍有保护层。

### 默认模式：本版重心

默认模式不追求通过关键词猜测命令是否安全，而是围绕**操作类型、访问对象、风险级别和用户确认**建立规则。建议默认模式至少区分：

- 普通读取：项目路径白名单内的普通文件自动允许。
- 敏感读取：按用户选择，`.env`、私钥等敏感文件在路径白名单内也直接读取，不做额外确认；这与只读模式的取舍一致，不构成保密或防泄露保证。
- 写入/编辑：路径白名单内直接执行；路径外执行前确认，展示路径、操作类型和差异摘要。
- 工作范围外文件：读取和写入都需要用户明确确认；路径解析失败返回工具错误，不把无法解析的目标自动视为已授权。
- Bash：用户级只读命令白名单和项目级前缀白名单命中时自动执行；用户级黑名单命中时取消自动放行，改为审批；其他命令审批。确认后仍不等同于沙箱隔离。
- 取消或拒绝：工具不执行，把结构化原因回传给模型；模型改用其他工具或方案时重新决策，不能沿用上一次授权。

默认模式的核心不是“所有操作都弹窗”，而是让低风险、可解释的操作保持流畅，把写入、任意命令和范围外访问变成明确的用户决策。

### 默认模式最终模型（2026-10-23 历史实现）

> 本节是 2026-10-23 的首版模型，保留用于理解设计演进。当前自动执行行为、21 命令表和审批选项以“权限收口方案（2026-10-29 已实现）”为准。

默认模式由四组规则组成：

- **用户级只读白名单（历史）**：代码内置、固定、不可动态修改；当时包含 12 个只读查询命令，逐命令校验参数和路径，不经过 shell，其中 `echo` 只接受字面量参数。当前为 21 个命令的两档表。
- **用户级危险后缀黑名单**：代码内置、固定、不可动态修改；只在项目命令前缀即将自动放行时，对指定工具的危险后缀做覆盖；命中后取消自动放行，改为审批，且不提供“批准并记录”。黑名单不做硬阻止；只读模式不使用，`allow` 模式忽略。
- **项目级命令前缀白名单**：只对固定的可记录工具族和安全子命令开放，用户选择“批准并记录”后写入项目规则。简单命令和受控 `&&`/`;` 链中的每个命令段都可记录；含 `||` 的链不提供新增记录；前缀至少包含程序和子命令；`npm run` 等包含脚本名；解释器、shell、危险后缀以及选项在子命令前的命令都不提供记录。
- **项目级路径白名单**：初始只有启动工作目录；路径外读取或写入时审批，用户选择“批准并记录”后新增。目录记录为目录，文件记录为文件；路径内 `read`、`write`、`edit` 直接执行，路径外审批。

#### 用户级只读白名单（2026-10-23 历史 12 命令表）

> 下表是首版 12 个命令，不是当前名单。2026-10-29 收口后当前固定表为 21 个命令：纯读 14 个（`echo`、`basename`、`dirname`、`pwd`、`realpath`、`ls`、`grep`、`cat`、`head`、`tail`、`wc`、`stat`、`du`、`diff`），逃逸口 7 个（`find`、`rg`、`sed`、`sort`、`uniq`、`tree`、`file`）。当前参数范围、平台差异和拒绝项见“权限收口方案”。

| 命令 | 允许形式（首版） |
| --- | --- |
| `echo` | 字面量参数，不经过 shell 展开 |
| `pwd` | 无参数 |
| `ls` | `-a -l -h -1 -F -d`，可组合；路径可省略，默认 `.` |
| `find` | 一个起始路径；`-maxdepth 0..32`、`-type f\|d`、`-name PATTERN`、`-print` |
| `grep` | `-n -i -r -E -F`、pattern、至少一个路径 |
| `cat` | `-b -e -n -s -t -v`、一个以上普通文件 |
| `head` | `-n N`（N≥0）、`-q -v`、一个以上普通文件 |
| `tail` | `-n N` 或 `-n +N`、`-q -v`、一个以上普通文件；拒绝 `-f -F -r` |
| `wc` | `-l -w -c -m -L`、一个以上普通文件 |
| `stat` | 一个以上路径，不接受选项 |
| `du` | `-a -c -h -k -m -s -x`、`-d 0..32`；路径可省略，默认 `.` |
| `diff` | `-a -b -B -c -E -i -N -q -r -t -u -w`、`-U N`；恰好两个路径；退出码 1 视为有差异 |

- 首版的 12 个命令在只读和默认模式中共用同一张固定表；`allow` 模式不限制。
- 当前固定表和分段器已经扩展：长选项 `--name value` 与 `--name=value`、短选项粘连取值（如 `-n20`）都可按封闭表接受；表外选项仍然拒绝。两种模式共用最多 8 段的分段器，支持管道和 `&&`/`||`/`;`，首段可虚拟 `cd`。
- 新增文件读取命令只读取普通文件；`diff -r` 可接目录。
- 路径参数走项目路径白名单：只读模式只允许启动工作目录；默认模式路径外进入审批，会话路径授权沿用同一套目录/文件语义。
- 未命中白名单的变体不是“降级执行”：只读模式拒绝，默认模式审批。首版“只读恰好两段管道、默认模式管道一律审批”已被 2026-10-29 的统一分段器取代。

#### 可记录的项目命令前缀（固定范围）

只有以下工具族和安全子命令可以写入项目规则；其他命令不能“批准并记录”，但可按条件“允许本次”或“本会话内允许”。

- **Git**：`status`、`log`、`show`、`diff`、`blame`、`grep`、`ls-files`、`ls-tree`、`rev-parse`、`describe`、`shortlog`、`cat-file`、`show-ref`、`for-each-ref`、`merge-base`、`fsck`、`help`、`version`。`add`、`commit`、`push`、`reset`、`clean`、`checkout`、`restore`、`switch`、`merge`、`rebase`、`fetch`、`pull`、`branch`、`tag`、`remote`、`config`、`submodule`、`filter-*`、`update-ref`、`reflog`、`gc` 等不提供记录。
- **Go**：`test`、`build`、`run`、`vet`、`doc`、`list`、`version`。
- **Cargo**：`test`、`build`、`run`、`check`、`clippy`、`bench`、`doc`、`metadata`、`tree`、`version`。
- **npm/yarn/pnpm/bun**：`run`、`test`、`start`；`yarn`、`pnpm`、`bun` 另允许 `build`。
- **make**：`make <target>`。

前缀生成规则：

- Git、Go、Cargo 取程序和子命令两个 token，例如 `go test`、`git log`、`cargo check`。
- `npm/yarn/pnpm/bun run` 取程序、`run` 和脚本名三个 token，例如 `npm run build`；`test`、`start` 及 `yarn/pnpm/bun build` 取两个 token。
- `make` 取程序和目标两个 token，例如 `make test`。
- 选项出现在子命令之前时不记录，例如 `git -C dir status`、`npm --prefix dir run build`、`make -f build.mk test`。
- 前缀按 token 精确匹配；`npm run build` 不匹配 `npm run build:prod`。
- 记录后，带其他路径或参数的命令仍按前缀自动放行；可识别路径参数仍需通过项目路径白名单。受控 `&&`/`;` 链会一次审批并记录多个分段前缀，后续按同样规则逐段检查；含 `||` 的链不提供新增记录。

代价：`pytest`、`mvn`、`gradle`、`dotnet`、`docker`、`gh` 等首版不记录，每次需要允许一次；后续可按需加入可记录工具族。

#### 用户级危险后缀黑名单（固定）

| 工具族 | 危险后缀 |
| --- | --- |
| Git | `--output`、`--open-files-in-pager`、`--paginate`、`--ext-diff`、`--textconv`、`--filters`、`--no-index`、`--exec-path`、`--upload-pack`、`--receive-pack`、`-c`、`--config-env`、`--git-dir`、`--work-tree` |
| Go | `-exec`、`-toolexec`、`-vettool` |
| Cargo | `--config`、`--manifest-path` |
| npm/yarn/pnpm/bun | `--prefix`、`--script-shell`、`--shell`、`--cwd`、`--dir` |
| make | `-f`、`--file`、`-C`、`--directory`、`-I`、`--include-dir`、`--eval` |

- 只在项目前缀即将自动放行时检查；命中后进入审批，且不提供记录。
- 只读模式不使用；`allow` 模式忽略。
- 不列程序级危险命令：`rm`、`sudo`、`curl`、`python`、`npm install`、`git push` 等本来就不在可记录集合，每次都会审批。
- `find -delete` 不进入黑名单：`find` 不在可记录集合，安全形式由用户级白名单处理，危险形式自然进入审批或拒绝。
- 黑名单不是穷举；被记录的项目脚本、测试和 make 目标内部仍可执行任意操作，不能当作沙箱。

#### 匹配与执行方式（2026-10-24 历史实现）

> 以下保留首版匹配和执行说明。2026-10-29 起两种模式共用 `parseShellCommand` 分段器和受控执行器，管道、控制运算符与三种尾部重定向均已纳入；当前规则见“权限收口方案”。

- 简单命令继续复用引号感知 tokenizer；当时默认模式用 `bash_chain.go` 识别顶层 `&&`、`||` 和 `;`，只读模式用独立的两段查询管道解析器。2026-10-29 收口后两种模式共用同一个分段器，旧的 `readonly_pipeline.go` 已删除。
- 用户级白名单逐命令解析参数；项目前缀用 token 切片比较；黑名单按每个分段检查 token 集合，`--option=value` 取 `--option` 后匹配。
- 不对原始命令使用 `strings.HasPrefix` 或 `strings.Contains`；路径使用现有 scope 解析，不对路径字符串做前缀比较；`cd` 后的相对路径按虚拟工作目录解析。
- 受控 `&&`、`||`、`;` 链只有所有分段都能直接执行、路径通过检查且未命中危险后缀时才自动执行；按 raw exit code 实现短路，所有分段使用直接 `exec`，不经过 shell。`&&`/`;` 可批量记录，含 `||` 的链不提供新增记录。当前管道中的可记录段沿用同样规则。
- 当时只读模式仅支持两段固定查询管道，默认模式管道仍需审批；2026-10-29 收口后两种模式都支持多段管道和 `&&`/`||`/`;`，管道退出码取最后一段、不设 pipefail。重定向只认三种尾部安全形式，其他重定向和未识别 shell 语法继续一次性审批或拒绝。

#### 规则存放位置与维护方式

- 用户级白名单和黑名单是固定策略，分别保存在 `internal/tool/permission_whitelist.go` 和 `internal/tool/permission_blacklist.go`，随程序编译进二进制。
- 启动后构建内存 map/set；每次工具调用按命令名或工具族做 O(1) 查询，不读取磁盘、不解析 JSON、不依赖项目文件。
- 白名单文件登记命令和对应规则/解析入口；具体参数解析可以继续放在 `restricted_bash.go` 或独立文件，但名单集中维护。
- 黑名单文件按工具族保存危险后缀；新增条目必须写明工具和精确 token 或前缀，不设立“全局危险命令”清单。
- 表驱动测试集中放在 `permission_rules_test.go`，覆盖每条白名单命令和黑名单后缀；每次增删改规则同时更新测试。
- `/permissions` 从内存表生成排序后的只读快照，不直接暴露可变 map。
- 项目级动态规则仍存 `.johnny/permissions.local.json`；用户级名单不进入该文件，也不支持用户运行时修改。
- `docs/versions/v0.7.md` 只保留规则说明和名单快照；完整名单以代码为准，避免文档与实现漂移。
- 如果未来出现非 Go 维护者高频改名单的需求，再评估 `go:embed` + JSON；当前不引入运行时数据文件。

#### 判断顺序（2026-10-23 历史）

> 当前判断顺序包含固定查询两档、项目前缀、会话授权和逐段路径检查，见“权限收口方案 → 新的判断顺序”。

自动执行必须同时满足：未命中危险后缀；命令命中用户级只读白名单或已记录的项目前缀；文件工具或查询命令的路径在项目路径白名单内。项目前缀命令还会检查可识别的路径参数。

1. 项目前缀自动放行候选命中危险后缀黑名单 → 审批，且不提供记录。
2. 文件工具、用户级白名单查询或项目前缀命令的可识别路径参数不在项目路径白名单 → 审批。
3. 用户级只读白名单完整形式命中，或项目前缀白名单命中且路径检查通过 → 自动执行。
4. 其他 → 审批。

- 项目前缀命令会检查形似路径的 token 和常见选项值；脚本、测试和构建目标内部访问无法静态限制，这是已知限制。
- 只读模式只使用用户级只读命令白名单和启动工作目录路径范围；忽略项目级命令/路径规则和危险后缀黑名单；非白名单 Bash 拒绝。
- `allow` 模式不应用任何命令/路径规则。
- 敏感文件没有额外保护；路径白名单内的 `.env`、私钥、`.git`、`.johnny` 权限文件都可以直接读写。这是明确的取舍：路径白名单不是安全边界，不能防止模型改写权限规则或 Git hooks。
- 项目级动态规则（命令前缀、路径）存放在项目根目录的 `.johnny/permissions.local.json`；用户级固定名单不写入该文件。项目规则只在 TUI 启动前加载，不热重载；加载前展示并确认，记录内容哈希，文件变化后重新确认。
- 2026-10-23 的默认值方案为：默认模式是不传 `--permission-mode` 时的默认值，`allow` 必须显式选择。2026-10-25 起开发阶段 CLI 默认改为 `allow`，`default` 仍可显式启用逐次审批。
- 本版原定不引入 `--add-dir`、OS sandbox、分类器或会话级授权；额外路径通过“批准并记录”加入项目路径白名单。其中会话级授权已在 2026-10-29 的收口方案中改为引入，见“权限收口方案”。
- `/permissions` 展示固定白名单、危险后缀黑名单和项目规则，支持删除/清空项目规则；项目规则的新增只通过审批面板。
- 审批结果写入 JSONL：工具调用 ID、操作目标、允许/拒绝/记录、决策来源和原因；拒绝原因作为工具结果回传模型。Ctrl+C 取消本轮单独记录，不属于审批选项。
- 本版只允许终端 TUI；参数任务、管道和重定向在入口处直接拒绝，不读取配置，也不打开 `/dev/tty`。


## 默认模式审批调研（2026-10-23）

本轮讨论默认模式的逐次审批。参考：

- Claude Code：本地 CLI 2.1.236 的 `--help`、`auto-mode defaults`，以及官方 [Permission modes](https://code.claude.com/docs/en/permission-modes)、[Configure permissions](https://code.claude.com/docs/en/permissions)。
- Codex：本地源码 clone `openai/codex`，commit `d681745`（2026-10-23），以及官方 [Agent approvals & security](https://learn.chatgpt.com/codex/agent-approvals-security)、[Rules](https://learn.chatgpt.com/docs/agent-configuration/rules)、[Sandboxing](https://learn.chatgpt.com/codex/sandboxing)。

### Claude Code 的 Manual 模式

Claude Code 当前有 `manual`（`default` 别名）、`acceptEdits`、`plan`、`auto`、`dontAsk`、`bypassPermissions` 六种模式。与我们的默认模式最接近的是 `manual`；`auto` 是分类器审查模式，`dontAsk` 是非交互式自动拒绝模式，二者不作为首切片目标。

Manual 模式的实际规则：

- 工作目录和 additional directories 内的读取自动允许。
- 内置只读 Bash 集合自动允许，包括 `ls`、`cat`、`echo`、`pwd`、`head`、`tail`、`grep`、`find`、`wc`、`which`、`diff`、`stat`、`du`、`cd` 和只读形式的 `git`。
- 文件写入/编辑、其他 Bash、网络访问需要审批；受保护路径（`.git`、`.claude`、shell 启动文件等）即使有 allow 规则也会提示。
- 权限规则按 deny → ask → allow 匹配，先命中者生效，规则具体程度不改变顺序。
- Bash 规则匹配命令文本，不是安全边界；官方对复合命令、包装器、重定向、`find -delete/-exec` 有专门处理，但仍明确说明不能替代 sandbox。
- 非交互 `-p`/SDK：需要审批的调用直接拒绝，除非 allow 规则、hook、callback 或权限提示工具批准；`dontAsk` 模式自动拒绝。
- 拒绝语义：带备注的 No 会把备注作为拒绝原因回传，模型继续；主对话中不带备注的 No 会结束本轮；Esc 取消。

审批提示和记忆：

- 展示工具类型、命令/目标、原因；选项包括 Yes、Yes and don't ask again、Yes and switch to auto mode、No；Tab 可给 Yes/No 添加备注，Esc 取消。
- Bash 的“不再询问”按仓库和命令永久保存到 `.claude/settings.local.json`；文件编辑的“不再询问”仅本会话有效；复合命令会按子命令拆成最多 5 条规则。
- 如果提示无法完整展示授权范围，只提供一次性允许，不提供“不再询问”。
- 关键路径的 `rm`/`rmdir` 等即使命中 allow 规则仍需要确认。

### Codex 的 Default 模式

Codex 提供三个权限预设：Read Only、Default（workspace-write）、Full Access；另有可选的 Approve for me（Guardian 自动审查）。

关键设计是 **sandbox 与 approval policy 分离**：

- Default = `workspace-write` sandbox + `on-request` approval。工作区内的读写和命令在 sandbox 内自动运行；只有越过 sandbox 边界（工作区外写入、网络等）才询问用户。
- approval policy 有 `on-request`、`never`、`granular`、`untrusted`（内部）；`granular` 可以按 sandbox_approval、rules、skill_approval、request_permissions、mcp_elicitations 分别允许或自动拒绝。
- 非交互 `codex exec` 默认 `never`；遇到需要审批的请求直接报不支持/拒绝，不等待 stdin。
- Guardian auto-review 只处理已经需要审批的动作，审查或解析失败时 fail closed，不扩大 sandbox 权限。
- Full Access 同时移除 sandbox 和审批保护。

审批提示和记忆：

- 命令：Yes, proceed；Yes, and don't ask again for commands that start with `<prefix>`；有时提供 Yes, and don't ask again for this command in this session；No, continue without running it；No, and tell Codex what to do differently。
- 文件修改：Yes, proceed；Yes, and don't ask again for these files（本会话）；No。
- 网络：just once、allow host for this conversation、allow host in future、block host in future。
- 决策类型包括 Accept、AcceptForSession、AcceptWithExecpolicyAmendment、ApplyNetworkPolicyAmendment、Decline、Cancel；多个审批请求排队，Ctrl+C 清空队列。
- 规则使用 Starlark `prefix_rule`，按命令参数前缀匹配；多个规则命中时 block > prompt > permit。项目规则只在项目受信任时加载，“不再询问”写入 `~/.codex/rules/default.rules`，需要重启。
- 前缀匹配不是语义边界；复杂 shell 不会可靠拆分，官方要求用 `codex execpolicy check` 验证。

### 对照与对首切片的含义

| 维度 | Claude Manual | Codex Default | 对本项目的含义 |
| --- | --- | --- | --- |
| 自动放行 | 工作区内读取 + 只读 Bash | sandbox 内工作区读写/命令 | Codex 依赖 sandbox；我们没有，不能直接照搬 |
| 写入/编辑 | 每次提示 | 工作区内自动 | 路径白名单内自动，路径外审批 |
| 任意 Bash | 提示 | sandbox 内自动，越界提示 | 用户级只读白名单/项目前缀白名单自动，其余审批 |
| 黑名单 | 内置只读集合和 deny 规则 | block > prompt > permit | 用户级固定危险后缀；危险程序不进入可记录集合 |
| 授权记忆 | 永久/会话规则 | 会话/前缀规则 | 项目级前缀白名单 + 路径白名单 |
| 非交互 | 拒绝 | 拒绝/不支持 | 拒绝并返回原因 |
| 安全边界 | 规则 + hook + sandbox | sandbox + 审批 | 审批不是沙箱 |

最终模型见上方“默认模式最终模型（2026-10-23 收敛）”。默认模式不再采用“所有写入每次确认”或“只允许本次”的旧建议。

## 只读模式第一切片（2026-10-23 历史实现）

> 本节记录第一切片，保留为历史。当前只读模式使用 21 命令两档表和统一分段器，支持管道、`&&`/`||`/`;`、工作目录内虚拟 `cd` 和三种尾部安全重定向，见“权限收口方案”。

第一切片是只读模式的实现记录；当前 v0.7 已扩展默认模式，并只允许终端 TUI 入口。

### 启动与行为

```sh
johnny --permission-mode read-only
johnny --permission-mode allow
```

- 第一切片当时只接受 `read-only` 和 `allow`，默认 `allow`；随后扩展 `default`，并在一段时间内不传 `--permission-mode` 时使用 `default`。2026-10-25 起开发阶段 CLI 默认改为 `allow`；`--permission-mode default` 和 `read-only` 仍为显式选项。只允许在终端直接输入 `johnny` 进入 TUI。
- 只读模式保留四个工具定义，但 `write` / `edit` 在执行前返回权限错误，不产生文件修改。
- `read` 只允许读取启动工作目录内的普通文件；允许工作目录内绝对路径和 `.env` 等敏感文件（用户明确选择）。
- `bash` 只执行受限查询白名单，不经过 shell；额外允许两段固定查询管道，消费者只能是无路径的 `grep`、`head`、`tail` 或 `wc`；不允许重定向、命令替换、`&&`、`||`、`;`、多段管道和后台执行。
- 只读模式的系统提示会明确禁止修改，并建议需要写入或运行测试时切换到 `--permission-mode default`，由审批决定；`allow` 在 2026-10-25 起为开发阶段 CLI 默认，仍可显式选择。
- TUI header 显示 `权限：只读` 或 `权限：放行`；本版后续收敛为只允许终端 TUI 入口，参数任务和普通行模式不再开放。
- JSONL 元数据增加 `permission_mode`；权限拒绝继续作为普通工具错误进入模型历史和会话记录。

### 受限 Bash 白名单

| --- | --- |
| `pwd` | 无参数 |

| `find` | 一个起始路径；`-maxdepth 0..32`、`-type f\|d`、`-name PATTERN`、`-print`；拒绝 `-delete`、`-exec*`、`-ok*`、`-fprint*`、`-fls`、`-L`、`-H`、`-follow` 和布尔表达式 |

### 明确限制

- 这是工具策略层只读，不是 OS sandbox。允许的程序仍以当前用户权限运行，可能访问网络、读取 `.env` 并让内容进入模型与 JSONL。

- 只读模式按用户选择允许读取敏感文件，因此不能把“只读”理解为保密或防泄露。

## 权限收口方案（2026-10-29 已实现）

**状态：代码与文档已完成，并通过全量测试和独立复核；用户联合验收仍待安排。** 本节是当前自动执行行为的唯一说明，取代前文中与之冲突的历史描述，包括：只读模式不支持 `&&`/`||`/`;`、默认模式管道一律审批、固定的 12 个命令、“不引入会话级授权”。前文标为 2026-10-23/24 历史实现的章节只保留设计演进和首版对照。五个默认设定已随用户授权实现一并确认，不再有“待确认”的阻塞项。

### 动机

默认模式审批率偏高，影响日常使用。已确认的来源：

- 单个 `|` 和重定向不被识别，整条命令审批；
- 固定查询只有 12 个命令，没有 `rg`、`tree`、`file`、`sort` 等常用读取工具；
- 参数形状卡得严，例如 `grep` 只认 `-n -i -r -E -F`，`-v -l -c -A -C --include` 都会审批；
- 可记录的命令族只有 5 类，其他命令（项目脚本、`pytest` 等）只有“允许本次”，同一条命令反复审批；
- 路径在工作目录外；
- 子任务和 workflow 任务把审批数量成倍放大。

目标是降低重复审批；只读模式继续限制为封闭的查询形式，拒绝明确的文件修改和外部程序执行选项。允许程序自身仍可能有副作用，例如 `sort` 使用系统临时文件。

### 不变的边界

- 仍是三种模式：`default`、`read-only`、`allow`；`allow` 不应用任何规则。
- 应用层策略，不是 OS sandbox；不引入 `--add-dir`、分类器、运行时模式切换。
- 工作目录内路径不额外保护：`.env`、私钥、`.git`、`.johnny` 权限文件都可读写。
- 所有自动放行的命令直接以 argv 执行，不经过 shell；命令替换、反引号、子 shell、heredoc、后台 `&`、循环、条件、变量展开仍不支持（默认模式审批，只读模式拒绝）；未引用的通配符在两种模式下都直接拒绝。
- 危险后缀取消自动放行，每次都需本次审批，不提供永久记录或会话授权（见“会话内允许”）。
- 可记录的项目命令前缀工具族（Git、Go、Cargo、npm/yarn/pnpm/bun、make）和固定危险后缀表保持不变。
- 项目规则的内容哈希信任、`remember` 每次询问、JSONL 审计不变。
### 命令分两档（已实现）

固定查询表按“有没有逃逸口”分成两档。两种模式共用同一张表，区别只在没有命中时：默认模式走项目前缀、会话授权或审批，只读模式直接拒绝并提示模型改用什么。只读模式的子任务（`access=read`）也用这张表，所以表里的命令直接决定子任务的搜索能力。

**纯读档（14 个）**：本身没有写文件和执行其他程序的参数。

- 成员：`echo`、`basename`、`dirname`、`pwd`、`realpath`、`ls`、`grep`、`cat`、`head`、`tail`、`wc`、`stat`、`du`、`diff`。
- 参数处理已实现：每个程序一张声明式封闭选项表，列出允许的布尔短/长选项、带值选项及其整数范围；长选项接受 `--name value` 和 `--name=value`，短选项接受粘连取值（如 `-n20`、`-C3`），`--` 之后按操作数处理。`grep` 支持 `-v -l -c -w -o -H -h -s -e -m -A -B -C --include --exclude --exclude-dir` 等；`ls` 支持排序和递归选项；`head`/`tail` 支持 `-c`；`wc` 支持 `-c`；`realpath` 支持 `-e -m -s -L -P -q -z`。
- 表外选项：默认模式审批，只读模式拒绝。纯读档仍拒绝会跟随符号链接、从文件读取参数或一直不返回的形式，例如 `grep -R`、`grep -f FILE`、`ls -L`/`-H`、`tail -f`、`wc --files0-from`。
- `stat` 的短选项在 GNU 和 BSD 上含义不同，参数表按运行平台封闭选择；未知平台只保留无取值选项。`file` 和 `tree` 的选项也按平台实际支持能力收紧。
- 取值选项的路径同样走路径检查；没有路径参数的形式（如 `grep PATTERN`）只允许作为管道的消费端。
- 文件读取类命令只接受普通文件；`diff -r` 可接目录，并强制 `--no-dereference`，避免递归比较跟随符号链接。`sort` 属于逃逸口档，即使拒绝写文件选项，输入超过内存缓冲时仍可能向系统临时目录写临时文件。

**逃逸口档（7 个）**：存在写文件或执行外部程序的参数，保留封闭白名单加语义解析，不用参数黑名单。

| 程序 | 开放的形式（已实现） | 固定查询表拒绝的形式 |
| --- | --- | --- |
| `find` | 多个起始路径；`-maxdepth`/`-mindepth 0..32`、`-type f\|d\|l`、`-name`/`-iname`/`-path`/`-ipath`、`-size`、`-mtime`/`-atime`/`-ctime`/`-mmin`/`-amin`/`-cmin`、`-print`/`-print0`/`-empty`/`-prune`，以及 `!`/`-not`、`-a`/`-and`、`-o`/`-or` 和括号组合 | `-delete`、`-exec*`、`-ok*`、`-fprint*`、`-fls`、`-L`、`-H`、`-follow` |
| `rg` | 常用搜索与输出选项（`-n -i -w -v -l -c -g -t -A -B -C -m -d --hidden --max-depth --max-columns` 等）；`-u` 可重复但仍不跟随符号链接；执行时强制加 `--no-config` | `--pre`、`--pre-glob`、`-z`/`--search-zip`、`-L`/`--follow`、`-f`/`--ignore-file` |
| `sed` | 只开放行号、`$` 或正则范围加 `p` 的打印脚本，例如 `1,20p`、`/foo/p`、`-e '1,5p'`；可带 `-n`、`-E`/`-r` | `-i`、`w`、`e`、`r` 命令和 `s///e`、`s///w` |
| `sort` | 常用排序选项，含键、分隔符和稳定排序；拒绝写文件和执行外部程序 | `-o`/`--output`、`-T`、`--compress-program`、`--files0-from`、`--sort=random`/`-R` |
| `uniq` | `-c -d -u -i -f -s -w`；选项和 `--` 必须写在输入文件之前，至多一个输入文件 | 第二个文件操作数（输出文件），以及操作数之后的选项 |
| `tree` | 常用显示选项、`-L 1..32`、`-I`/`-P` | `-o`、`-R`、`-l`、`--fromfile`/`--gitfile`/`--infofile` |
| `file` | `-b -i -k -h -n -N` 和 `--mime`/`--mime-type`/`--mime-encoding` 等 | `-C`、`-m`、`-f`、`-L`、`-p`、`-s`、`-S`；`MAGIC*` 环境变量由受限环境剥离 |

- 上一轮讨论把 `tree` 放进纯读档是错的：`tree -o FILE` 会写文件，归入逃逸口档。
- `jq` 未放行（`env`、`$ENV` 会读出环境变量）；`awk` 不放：程序文本里的 `system()` 无法靠参数表限制。
- 逃逸口档不使用参数黑名单：黑名单是开放世界，新版本程序增加的选项会悄悄通过；只读模式依赖封闭白名单。
- `rg` 强制 `--no-config`，并剥离受限环境中的 `RIPGREP_CONFIG_PATH` 等配置入口；`file` 的 `MAGIC*` 环境变量同样不会进入子进程。
- 这些限制只收窄可自动执行的命令形式，不是 OS 沙箱；被允许程序的内部行为、配置文件、系统临时文件和平台差异仍可能存在副作用。

### 复合命令与重定向（已实现）

两种模式使用同一个分段器 `parseShellCommand`，每个命令段独立判定；只读模式在验证阶段不启动任何进程，任一段不通过就整条拒绝。

- **语法**：用 `&&`、`||`、`;` 连接若干个管道，每个管道由 `|` 连接若干个命令段，`|` 绑定比控制运算符更紧。整条命令最多 8 个命令段；`cd <目录>` 只能是整条命令的第一段，必须是单个目录参数，不能带选项或重定向，不能参与管道，也不能紧邻 `||`（即 `cd x && ...`、`cd x ; ...` 可用）。后续段按虚拟工作目录解析相对路径，并继续检查是否仍在只读工作目录/项目路径白名单内。
- **判定**：每一段分别按固定表、项目前缀、会话授权、危险后缀和路径检查得出结论，全部自动放行才自动执行。默认模式下只要有一段需要审批，整条命令一次性审批，面板展示完整命令并标出需要审批的段。
- **执行**：直接 argv 加 OS pipe 接线，不经过 shell。`&&`、`||`、`;` 按 raw exit code 短路；管道的退出码取最后一段，不设 pipefail；消费端提前退出时取消并向生产端进程组发送终止，避免继续写满管道。
- **项目前缀命令可以作为管道生产端**，例如 `go test ./... | tail -20`，危险后缀按段检查；固定查询命令也可以作为生产端或消费端。
- **只读模式**：每一段都必须命中固定表，同样支持 `&&`、`||`、`;`、`|` 和工作目录内虚拟 `cd`；不支持项目前缀和会话授权。每段仍可能调用有自身副作用的程序（例如 `sort` 写系统临时文件），组合执行不代表零风险，只代表每段都在策略允许范围内。
- **重定向**：只认 `2>&1`、`>/dev/null`、`2>/dev/null` 三种形式，必须位于命令段末尾，可以按顺序出现；语义与 shell 一致，例如管道段里的 `2>&1` 会把 stderr 并入 stdout 送给下一段，`2>/dev/null` 丢弃 stderr。它们不创建真实文件，所以两种模式都可用。写入真实文件的重定向（`> out.txt`、`>> log`）、输入重定向、`&>`、`|&` 等其他形式：默认模式进入一次完整 shell 审批且不提供记录/会话授权，只读模式拒绝。
- **未识别 shell 语法**：后台 `&`、命令替换、子 shell、heredoc、循环、条件、变量展开等不会进入受控执行器。默认模式回退到一次完整 shell 审批，本次不提供“批准并记录”或“本会话内允许”；只读模式直接拒绝。
- **未引用的通配符**：默认和只读模式都直接拒绝，不进入审批。受控执行不展开通配符，给文件通配符加引号也不会展开；拒绝信息提示改用 `find -name '模式'`，并说明需要 shell 通配符时可使用 `--skip` 放行模式。这样不再为每次变化的 glob 重复询问，也不会通过完整 shell 回退绕过。
- **不存在的查询路径**：工作目录内不存在的路径不再在预检阶段报“路径不可用”，而是交给实际程序报告“文件不存在”。路径解析仍会展开已有祖先的符号链接并检查工作目录边界；工作目录外的路径仍按原有规则审批或拒绝。
- **拒绝提示**：解析失败时返回具体原因，不再统一显示“不支持该 shell 语法”。段数超限会给出实际段数并建议拆成多条 `bash` 调用；未引用的通配符会指出字符，说明受控执行不展开通配符、建议改用 `find -name`，并提示只有程序自己解释的选项值（如 `--include='*.php'`）才加引号；命令替换、输入重定向、未闭合引号等沿用各自的说明。查询解析器的错误文案使用中性表述，不再在默认模式的审批面板里显示“只读模式……”。默认模式的完整 shell 审批把同一原因放进审批面板的 `Reason`，`Detail` 继续保留原始错误。
- **命令查找**：裸程序名通过 `exec.LookPath` 查找，含路径分隔符的程序按命令段目录解析；不经过 shell，也不在找不到程序时回退到 shell 执行。
- **记录规则沿用现有链**：`&&`/`;` 可批量记录各段前缀，含 `||` 的链不提供新增记录；管道里的可记录段按同样规则处理。不可记录的直接命令段生成精确 argv 会话授权键，而不会回退到整条 shell。

### 会话内允许（已实现）

审批面板提供“本会话内允许”：只在当前 johnny 进程的内存里记住，不写项目规则文件，不进入 `~/.johnny/trusted_permissions.json`，进程退出即失效。它填补“允许本次”与“批准并记录”之间的空白：不可记录的命令也能只授权一次。面板上“允许本次”的语义没有改变；“本会话内允许”是独立的显式选项，不是“允许本次”的别名。

- **面板选项与顺序**：允许本次 / 拒绝本次 / 本会话内允许 / 批准并记录。默认焦点仍在拒绝。“批准并记录”只在可记录时出现；“本会话内允许”只在请求带有可记住的授权键时出现。点选“本会话内允许”时先写入授权，再回传允许决策，随后队列立即按新授权重检。
- **授权键**：
  - 路径外的 `read`/`write`/`edit`：与“批准并记录”相同，使用 `PathRule`，目录记目录、文件记文件，只存内存。
  - 可记录命令段：与“批准并记录”相同的命令前缀，按规范工作目录区分。
  - 其他命令段：该段的完整 argv（程序和全部参数）加有序重定向，按规范工作目录区分；参数不同就重新询问。这样授权的内容就是用户看到并批准的那一条，不会因为授权了 `./build.sh` 而放行 `./build.sh --deploy`。
  - 复合命令和管道逐段生成授权键，各段独立匹配；只有请求中的全部缺失命令和路径都被覆盖才算命中。
- **路径仍逐项检查**：即使命令段已有会话授权，新出现的路径仍要单独通过项目路径白名单或会话路径授权；路径检查失败不会被命令授权顺带放行。
- **不提供会话授权**：命中危险后缀的命令段（每次都问）；`remember`（v0.11 规定每次询问）；无法安全转成 argv 的完整 shell 回退请求；尚未被项目规则放行的非查询管道消费者。这些请求的面板不出现“本会话内允许”。最后一类可能把上游内容当脚本执行，完整 argv 无法限定输入，例如 `echo '脚本' | sh -`，需要每次审批；不能借助以前对单独 `sh -` 的会话授权放行。项目永久前缀的既有语义保持不变。
- **共享范围**：主 Agent、子任务、workflow 任务通过同一个 `ApprovalGate` 共享同一份授权，只在当前进程生命周期内有效，授权只看命令、工作目录和路径，与哪个 Agent 发起无关。子任务审批面板同样出现该选项并标明来源。`access=read` 的子任务仍走只读包装，不查询会话授权，只能用固定表；写入类子任务的文件范围护栏（`ScopeGuard`）继续生效，但它只拦截 `write`/`edit`，`bash` 不受限，仍不是安全边界。
- **队列重检**：创建授权后，审批队列里授权键相同的待审批请求在显示前重新检查，命中则自动放行，不再逐个弹出。workflow 里 5 个任务同时请求同一条命令时，只需点一次；创建授权后的后续请求也走同一入口。
- **拒绝和取消**：拒绝本次或取消本轮不会创建任何授权；被取消的审批不会写入会话授权库。
- **审计**：创建授权时写 `permission` 事件，决策为 `allow_session`，`session_commands` 带 `cwd` 和 `prefix` 或 `argv`/`redirects`，`session_paths` 带目录/文件规则；使用已有授权自动放行不另外写 `permission` 事件（与项目前缀自动放行一致，工具调用本身仍在 JSONL 中）。
- **管理**：`/permissions` 展示“本会话授权”一节（有界快照和单条截断）；`/permissions clear-session` 一次清除全部会话授权，用来撤销误点。

### 新的判断顺序

对每个命令段（文件工具视为一段）依次判断：

1. 命中危险后缀 → 审批，不提供记录和会话授权。
2. 可识别路径不在项目路径白名单（含已记录路径和会话授权的路径）→ 审批。
3. 命中固定表（纯读档或逃逸口档的开放形式）→ 自动执行。
4. 命中已记录的项目命令前缀 → 自动执行。
5. 命中会话授权 → 自动执行。
6. 其他 → 审批。

只读模式只做第 3 步和工作目录路径检查（含虚拟 `cd` 后的相对路径），不支持项目前缀和会话授权，其余一律拒绝。固定表里“表外选项”的处理见“命令分两档”。会话授权必须覆盖请求中的全部缺失命令键和路径键；只有部分命中时仍进入审批，并只把未覆盖的部分列为会话授权目标。

### 不做与暂不决定

- 不做：OS sandbox、`--add-dir`、分类器、运行时模式切换、awk、shell 变量与 glob 展开、写真实文件的重定向自动放行。
- 暂不决定：扩大可记录命令族（`pytest`、`mvn`、`gradle` 等）、`git add`/`git commit` 是否可记录，留待后续评估。
- 审批队列不做“合并相同请求”的独立面板；用会话授权后的队列重检达到类似效果。

### 独立复核与修正（2026-10-29）

实现完成后做了多角度对抗复核，确认并修正了以下问题，均有回归测试：

- **符号链接后的 `..`**：`link/../x` 原先按词法清理，可能把实际写到目录外的路径判成目录内，命令授权和路径授权都会因此错位。现在按内核顺序先展开链接再应用 `..`，工作目录、项目规则、会话授权和实际读写目标共用同一套解析。
- **管道消费者的输入**：未获项目规则放行的非查询管道消费者（例如 `echo '脚本' | sh -`）不再提供会话授权；否则同一 argv 在不同上游输入下可执行任意脚本。单次批准仍然可用。
- **取消与授权保存**：审批等待中被取消的请求不会再写入会话授权；点击已提交的决策不会被随后到达的取消改写成拒绝审计。
- **重复保存**：TUI 保存授权后，`ApprovalGate` 不再重复保存，`/permissions clear-session` 不会被排队中的旧决策“复活”。
- **授权键与显示**：授权键改用无歧义的编码，避免参数分隔符碰撞；面板逐项引用含特殊字符的参数，并在截断时说明还有多少个键。
- **BSD/GNU 参数差异**：`uniq` 拒绝操作数之后的选项，防止 BSD 把 `-c` 当输出文件；`stat` 按平台封闭选项；短选项取值统一粘连，避免被实际程序当成未解析的操作数。
- **递归比较符号链接**：`diff -r` 强制 `--no-dereference`；查询命令和工作目录之外的路径仍逐项检查。
- **命令不存在**：链中某条命令不存在时按 shell 的 127 语义继续执行 `||` 或 `;`，不再中断整条链；已知查询形式校验失败时会显示具体原因，而不是笼统说“不在白名单”。

### 真实模型观察后的提示补强（2026-10-29）

在只读模式下用真实模型探索一个中型 PHP 仓库（单轮、63 次模型请求、120 次工具调用），共 14 次拒绝：1 次 `git` 和 2 次路径不存在属于正常判定，其余 11 次都显示同一句“只读模式不支持该 shell 语法”。实际构成是 5 次命令段超过 8 段、6 次未引用的通配符（`--include=*.php`、`head *.conf` 等）；模型看不到原因，只能靠试错改成加引号或拆成多条调用。

解析器本身一直带有具体原因，只是只读模式把它替换成了固定文案。现在：

- 只读模式的拒绝内容改为“只读模式不支持该命令：具体原因”，并把处理建议写进原因本身；
- 段数检查提前到拆分完成后，能报出实际段数，例如“命令共 12 段，超过 8 段上限；请拆成多条 bash 调用”；

- 默认模式的完整 shell 审批原因同样展示具体原因，不再只说“需要 shell 审批”。

判定结果和允许范围没有变化，只改错误信息；回归测试在 `bash_chain_test.go`、`readonly_pipeline_test.go`、`default_chain_test.go`。

### 默认模式的审批引导（2026-10-29）

真实模型在默认模式下探索同类仓库（单轮、22 次模型请求、40 次工具调用、0 次失败），共 19 次审批：9 次未引用通配符、3 次超过 8 段、2 次 `git`、2 次命令替换、1 次循环、1 次 `find` 重复参数、1 次路径不存在。随后用更长的一轮验证（38 次模型请求、76 次工具调用、29 次审批），通配符仍占 16 次，路径不存在 5 次，说明只靠提示词不足以消除这类审批。完整 shell 回退按设计不提供会话授权，同一类写法换个参数就会再次询问。

- 默认模式系统提示改为明确说明“通配符不会被展开”：未引用的通配符会被直接拒绝，给文件通配符加引号也不会展开；查找文件用 `find -name '模式'`，只有程序自己解释的选项值（如 `--include='*.php'`）才加引号。一条命令不超过 8 段，长探索拆成多次；避免命令替换和 `for` 循环。
- 未引用的通配符在默认模式改为直接拒绝，不再回退到完整 shell 审批；只读模式原本就拒绝。拒绝信息给出替代写法，并说明需要 shell 通配符时可使用 `--skip` 放行模式。
- 工作目录内不存在的查询路径不再在预检阶段触发审批或报“路径不可用”，交给实际程序报告“文件不存在”；已有祖先的符号链接展开和范围检查保持不变。
- 查询解析器的错误文案去掉“只读模式”前缀，默认模式审批面板不再显示与实际模式不符的说明。
- `permission` 审计事件补记 `request_reason` 和 `request_detail`，分别保存“为什么需要审批”和解析器的具体说明，与用户选择的 `reason` 分开；已有会话授权自动放行仍不写审批事件。
- 判定顺序、允许范围和会话授权规则都没有变化；`for` 循环、命令替换等其余需要 shell 的语法仍走一次完整 shell 审批。

## 文件访问范围（已确认）

- 已确认不引入 `--add-dir`，初始路径只有启动工作目录；路径外访问通过审批中的“批准并记录”加入项目路径白名单，目录记目录、文件记文件。“本会话内允许”使用同样的路径规则，只记在进程内存中，退出即失效。
- `read`、`write`、`edit` 使用同一套路径检查；不能只检查路径字符串前缀。
- 相对路径、`..`、绝对路径、符号链接指向以及尚不存在的写入目标，都需要按实际访问对象判断。
- 工作范围外的访问允许用户明确批准，以支持跨目录任务。
- 在主目录等较大范围启动时，不能把整个范围内的凭据自动视为普通项目文件。
- 路径白名单不是安全边界：路径内 `.env`、私钥、`.git`、`.johnny` 权限文件都可直接读写。这是用户明确选择的取舍，不是“敏感文件保护”。
- 只读模式沿用启动工作目录范围，但允许读取 `.env`、私钥等敏感文件；默认模式在此基础上增加动态路径白名单和进程内会话路径授权。

实现时还需检查路径验证与实际打开文件之间的变化，不能把一次符号链接解析当作完整的隔离保障。

## Bash 授权与沙箱边界（部分已确认）

默认模式把 Bash 视为能够运行任意程序的入口，审批时展示完整命令和实际工作目录。用户级白名单和项目前缀只用于自动放行判断，不依靠 `rm`、`curl` 等关键词识别来承诺命令安全；管道、重定向、脚本、解释器和子进程都会影响实际行为。

- 用户级固定查询命令直接以 argv 执行，不经过 shell；默认模式和只读模式都使用统一的受控执行器。默认模式的 `echo` 等字面量命令只传递字面量参数。
- 项目前缀命令在记录后直接以 argv 执行，不经过 shell；受控 `&&`/`||`/`;`、管道和三种尾部安全重定向逐段按 token 匹配并使用虚拟工作目录。固定查询可以出现在默认和只读模式；项目前缀只用于默认模式。
- 不属于受控分段器的其他命令不会自动执行：默认模式做一次完整 shell 审批，本次不提供记录或会话授权；只读模式直接拒绝。审批通过后仍具有当前用户的文件与网络权限。
- 任何自动放行都不是沙箱；路径白名单也约束不了项目前缀命令内部的路径访问。

**用户允许一条 Bash 命令后，如果没有系统沙箱，该进程仍具有当前用户的文件与网络权限。** 文件工具的工作范围检查无法约束已经获准启动的任意程序。

统一授权与交互规则已经收敛；按当前确认范围，v0.7 不包含 OS sandbox。应用层审批、命令白名单和环境过滤不能阻止获准命令访问范围外文件或网络；后续版本是否引入可验证的操作系统限制或容器方案，需要另行决策。

## 审批交互（2026-10-23 确认，2026-10-29 增补）

- 审批面板按条件提供四个选项：允许本次、拒绝本次、本会话内允许、批准并记录；不是固定三项。默认焦点在拒绝。
- “本会话内允许”只在请求带有可记住的授权键时出现，与“允许本次”语义不同：它把命令前缀加规范工作目录、不可记录命令的完整 argv 加有序重定向，或路径规则记入当前进程内存。危险后缀、`remember` 和完整 shell 回退请求不出现该选项。
- “取消本轮”不作为审批选项；等待审批期间 Ctrl+C 取消本轮，等待当前操作收尾后回到输入区。
- 默认焦点放在“拒绝本次”，避免回车误放行。
- 展示工具名、工作目录、目标文件或完整命令，以及需要确认的原因；写入、编辑提供内容或差异预览。
- “批准并记录”只在可记录时出现，并显示将记录的命令前缀数组或路径。受控 `&&`/`;` 链可以一次记录多个分段；含 `||` 的链、解释器/shell/包装器、无法形成稳定前缀或无法安全转成 argv 的完整 shell 回退请求，只显示允许本次和拒绝本次。
- 路径外的 `read` / `write` / `edit` 的“批准并记录”记录路径；命令的“批准并记录”记录命令前缀；两者都使用同一套路径/前缀语义，会话授权只是不落盘。
- 拒绝作为明确的工具结果回传，允许模型解释原因或提出其他经过授权的方案；要停止整轮使用 Ctrl+C。
- 多个工具按原有顺序分别检查；批准一个操作不自动批准随后出现的操作。创建会话授权后，队列中同键的待审批请求会自动放行，这是唯一的队列合并效果，不另设合并面板。
- 审批决策写入 JSONL；创建会话授权记为 `allow_session` 并带授权键，使用已有授权不重复写审批事件；Ctrl+C 取消本轮单独记录，不混同于审批拒绝。

本版只支持在终端直接输入 `johnny` 进入 TUI 交互模式。参数任务、管道和重定向在入口处直接拒绝，不打开 `/dev/tty`，也不读取模型配置。

## 凭据与记录（部分已确认）

- 现有模型配置保持原位，模型请求仍由程序使用凭据；不把 API Key 注入系统提示或模型上下文。
- Bash 子进程的环境单独构造，避免继承程序专用的模型认证字段；具体保留与移除的环境项需在实现前列明。

环境过滤减少意外传递；在没有系统沙箱时，它不能阻止获准的 Bash 读取磁盘配置或其他可访问的凭据。

3. 范围外路径、`..`、符号链接和不存在的写入目标按实际访问对象检查，不因路径写法不同绕过决策。

5. 拒绝结果正确回传到模型并进入合法会话历史，跨三种模型协议继续工作；新的工具调用重新检查。
6. 参数任务、管道和重定向在读取配置前被拒绝，不请求模型，也不等待审批。
7. 使用测试凭据验证子进程环境、敏感文件访问和审计记录；原位真实配置保持不变。
8. 如纳入系统沙箱，使用实际子进程验证获准命令仍无法越过约定的文件或网络边界；仅命令文本检查不算通过。
9. （历史）用户级白名单 12 个命令的允许形式和拒绝形式符合约定，`echo` 只传递字面量参数。当前 21 命令的对应场景见 15–16。

11. `rm`、`sudo`、`curl`、`python`、`npm install`、`git push` 等不可记录命令每次审批，面板不出现“批准并记录”；有可记住的 argv 时出现“本会话内允许”。
12. `cd <目录> && <简单命令>`、`||`、`;` 链按段预检和直接执行；路径、危险后缀和已记录前缀逐段生效，raw exit code 决定短路；`&&`/`;` 可批量记录，含 `||` 的链只能本次允许。
13. （历史）只读模式的 `find | head`、`ls | wc -l`、`cat | wc -l` 等两段固定查询管道直接执行；三段管道、默认模式管道、重定向、命令替换、循环和解释器继续一次性审批或拒绝。当前只读模式支持多段管道和 `&&`/`||`/`;`，对应场景见 18–19。
14. 审批面板按条件提供“允许本次 / 拒绝本次 / 本会话内允许 / 批准并记录”，默认焦点在拒绝；“本会话内允许”只在有授权键时出现，“批准并记录”只在可记录时出现；Ctrl+C 取消本轮且后续工具不执行。
