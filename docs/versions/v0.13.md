# v0.13 · Workflow

**状态：已实现（2026-10-28），待与 v0.12、v0.7 一起验收。** 版本主题由 Agent Team 改为 Workflow：主 Agent 先声明分步大纲，再逐步补细节并启动一批并行子 Agent，子 Agent 之间不通信。本文记录已确认的产品行为、界面、技术方案、调研和实现记录。自动化测试与 PTY 终端模拟验收已通过；真实模型下的长时间观察和用户验收与 v0.12、v0.7 一起进行。

**验收安排：** v0.12 SubAgent 已实现但验收后置，v0.13 完成后与 v0.7 权限收口一起验收。因此 v0.13 建立在尚未经过真实模型观察和用户验收的 v0.12 之上；验收时若发现底座问题，需要回头调整，v0.13 的改动也需要回归 v0.12 的 19 个验收场景。

[返回总体路线图](../johnny-code-roadmap.md)

## 本版目标

让主 Agent 把较大的任务拆成**有顺序的几步**，每一步内由多个子 Agent 并行执行。主 Agent 负责规划和判断：先声明大纲，轮到每一步时再决定这一步派几个子 Agent、各做什么；一步全部结束后，主 Agent 看到这一步的所有报告，再规划下一步。

Workflow 不是新的权限层，也不是脚本语言。子 Agent 之间不互相发消息，只通过主 Agent 交接结果。成员间消息、共享任务板、用户与成员直接对话、成员长期存在与恢复，这些 Agent Team 的能力本版不做。

## 与 v0.12 的边界

v0.12 提供底座，v0.13 直接复用：

- Manager 与子任务登记、收件箱、结果注入和空闲唤醒；
- 审批来源标注与审批队列；
- 每个 Agent 独立的会话 JSONL 和父子关联；
- 取消沿父子关系传递；
- 写入类任务的文件范围（v0.13 可能升级为一等的文件所有权）。

v0.13 新增：

- 工作流的大纲登记与进度状态；
- 步骤屏障：同一步的任务全部结束后，才合并送回主 Agent 并唤醒一次；
- 批量、原子地启动一步内的多个任务；
- 更高的并行数，多出的任务排队；
- 任务区界面，同时承载 v0.12 的单个子任务。

`task` 继续用于单个异步委派，行为不变。

## v0.12 的实际底座

以下是 v0.12 代码中已经存在的行为，是 v0.13 讨论的起点。细节见 [v0.12](v0.12.md)。

| 方面 | 现状 |
| --- | --- |
| 派出方式 | 只有主 Agent 能通过 `task` 工具派出；子 Agent 没有 `task` 和 `remember`，只有一层 |
| 并发与限额 | 同时最多 3 个（`subagent.MaxConcurrent`），每个最多 30 次模型请求、20 分钟 |
| 通信方向 | 单向：子任务结束时把一份报告送回主 Agent。派出后无法给子任务追加指令，子任务之间不通信 |
| 生命周期 | 子任务结束即销毁，不能恢复，也不能继续对话 |
| 收件箱 | 只有主 Agent 有。`Conversation.Enqueue` 线程安全，内容是“文本 + 来源”，下一次模型请求前合并注入（最多 24 KiB）；`RunInbox` 在空闲时唤醒一轮 |
| 文件范围 | `FileClaims` 登记写入类子任务的路径，范围不能重叠；`ScopeGuard` 只拦截 `write`/`edit`，`bash` 不受限 |
| 审批 | `Origin` 标明请求来自哪个子任务；TUI 里是先进先出队列和模态面板；审批网关能观察“正在等待审批” |
| 取消 | 只有整体取消（`Ctrl+C`、`/exit`），没有单独停止某个子任务 |
| 界面 | 常驻区每个子任务一行：编号、描述、耗时、状态；看不到过程，没有按成员切换的视图 |
| 日志 | 每个子 Agent 独立 JSONL，主会话记录 `subagent_start`/`subagent_end`/`inject` |
| 成本 | 子任务 token 没有汇总到 `/context`，界面上看不到成员的用量 |

v0.12 明确留下的缺口：单独停止某个子任务、`/tasks` 列表、子任务恢复与继续对话、展示子 Agent 过程、自定义 Agent 角色、子任务独立模型、`bash` 不受文件范围约束。这些缺口本版都不处理，唯一的例外是任务区界面的调整（见“界面”）。

## 已确认的产品行为

1. **主 Agent 驱动，没有预写脚本。** 主 Agent 规划每一步，并在每步开始前自己决定派几个子 Agent。运行时只负责登记大纲、按顺序启动、等待整步结束、送回结果。
2. **大纲先行。** 主 Agent 先调用 `workflow` 工具，声明总步数以及每一步的标题和目标，不写任务细节。运行时登记这个工作流，界面显示整体进度。
3. **逐步补细节并启动。** 轮到某一步时，主 Agent 再调用 `workflow`，给出这一步的任务：每个任务的描述、提示词、`kind`（`fresh`/`fork`）、`access`（`read`/`write`）和 `paths`。这一批任务原子地校验和启动：范围重叠、超限或参数错误则整批拒绝。启动后主 Agent 不等待，可以结束本轮。
4. **整步送回。** 一步内的任务全部结束后，所有报告合并成一条送回主 Agent，只唤醒一次。每份报告沿用 v0.12 的格式与数据声明，最多 8 KiB，每步的报告都进入主 Agent 上下文。送回时附带工作流进度（已完成哪几步、下一步是什么），计划不依赖主 Agent 的记忆，也不会因上下文压缩而丢失。
5. **严格按顺序。** 步骤必须按大纲顺序启动，上一步没结束不能启动下一步。同一时间只有一个进行中的工作流。
6. **大纲不能中途修改。** 主 Agent 只能提前结束工作流，剩余步骤标为未执行；需要新计划时另起一个工作流。这样大纲就是用户一开始看到并默认的计划。
7. **数量上限（起始值）。** 大纲最多 10 步，每步最多 8 个任务，同时运行最多 5 个，多出的排队。等真实模型观察后再调整。
8. **失败不终止工作流。** 某步有任务失败或超时，整步照常送回并带上失败信息，由主 Agent 决定重试、换方案或结束。
9. **自动推进。** 步骤之间不要求用户确认。`Ctrl+C` 取消整个工作流：取消所有运行中的任务，剩余步骤标为未执行。`/exit` 的行为与 v0.12 一致。
10. **入口。** `workflow` 是主 Agent 调用的工具，和 `task` 一样只在 TUI 入口注册。用户仍然用自然语言提出要求，不新增斜杠命令。

第 5 条的“同一时间只有一个工作流”和第 10 条的“不设斜杠命令”是讨论中采用的默认假设，用户没有提出异议。第 4 条的报告总量上限见“技术方案”。

## 界面（已确认）

任务区放在输入框下边线之下，与主 Agent 的对话记录分开。空闲时的布局：

```
（上方是主 Agent 的对话记录）
────────────────────────────────────────
> 输入框
────────────────────────────────────────
workflow 重构日志模块  2/4
✓ 1 调研现状
◆ 2 并行改造各子模块    3/5 个任务完成
    ◆ a1b2 改造 parser · 1m05s · 运行中
    ◆ c3d4 改造 writer · 1m05s · 等待审批
○ 3 集成测试
○ 4 汇总
◆ ef56 查日志 · 12s · 运行中
空闲 · Enter 发送 · Alt+Enter 换行 · /exit 退出
```

- **位置。** 任务区夹在输入框下边线和页脚之间，页脚仍在最后一行。主 Agent 忙碌时没有输入框，任务区在本轮工具过程和状态行之间，与 v0.12 一致。审批面板仍然独占动态区域。
- **内容。** 一个任务区同时放 workflow 和 v0.12 的单个子任务，workflow 在前，单个子任务保持一行格式。workflow 的当前步骤下只列运行中和等待审批的任务，已完成的只计入“3/5”。
- **结束提示。** 单个子任务结束时，仍往对话记录打印一行完成、失败或取消。workflow 不逐任务打印，只在每步结束和整个工作流结束时各打印一行汇总；单个任务失败的原因由主 Agent 在汇总里说明。
- **高度。** 任务区最多占终端高度的三分之一。放不下时按优先级保留：标题行、当前步骤及其运行中的任务、未开始的步骤，最后是已完成的步骤，折叠成一行。终端太矮时只显示一行摘要，例如 `workflow 2/4 · 3/5 个任务 · 1 个等待审批`。
- **对 v0.12 的影响。** v0.12 空闲时的子任务行原本在输入框上边线之上，这次移到下边线之下，输入框光标位置的计算和相关 TUI 测试随之调整，v0.12 文档同步更新。任务区每多一行，可见的对话记录就少一行，所以需要高度上限。

## 暂不做

- 成员间消息、mailbox、共享任务板、用户与成员直接对话、成员长期存在与恢复（Agent Team 的层级 2 至 4）；
- 脚本语言、循环和条件分支，大纲的中途修改；
- 工作流的持久化和恢复（沿用 v0.12，不支持恢复）；
- 无屏障的流水线（Claude 的 `pipeline()`）；
- worktree 隔离、单独的子任务模型、自定义 Agent 角色；
- 用户手写的工作流文件和 `/workflow` 斜杠命令；
- 非 TUI 入口。

## 协作梯度

| 层级 | 形态 |
| --- | --- |
| 0 | 并行独立子任务（v0.12） |
| 1 | 主从协作：主 Agent 分派，成员回报，成员之间不通信 |
| 2 | 成员之间互相发消息，主 Agent 仲裁 |
| 3 | 共享任务板，成员自行认领，带依赖 |
| 4 | 成员长期存在，可恢复，用户可直接和成员对话 |

本版选择层级 1，并加上步骤编排：主 Agent 分派，成员回报，成员之间不通信；一步内并行，步与步之间由主 Agent 衔接。层级 2 至 4 属于 Agent Team，本版不做。

## 候选场景

1. 实现者与审查者来回迭代：只能拆成固定的几步（实现、审查、修复），不能无限循环；
2. 后端、前端、测试按模块分工并行开发：先用一步确定接口约定，再用一步并行实现，适合本版；
3. 多个研究者提出并互相质疑不同方案：先用一步让多个研究者各自提方案，再用一步让多个审查者读取全部方案并质疑，成员之间仍不直接对话；
4. 规划、实现、测试流水线：由主 Agent 按步骤编排，适合本版。

## 调研记录（2026-10-28）

### Agent Team 方向（本版未采用）

**Claude Code agent teams**（https://code.claude.com/docs/en/agent-teams）：

- 实验性，默认关闭，需要 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`，仅交互模式；
- lead 是主会话，teammates 是各自独立的会话和上下文；
- 共享任务列表有 pending / in-progress / completed 状态和依赖，认领任务用文件锁；
- 每个成员有 mailbox，`SendMessage` 自动投递，成员空闲时把最终结果通知 lead；
- 用户可以选中某个成员，查看并发消息；
- 权限继承 lead，审批冒泡到 lead；Agent 消息不能代表用户同意，也不能转授被拒绝的操作；
- 推荐 3 到 5 人，没有硬上限，成本随人数大致线性增长；
- 官方限制：成员不随会话恢复、任务状态可能滞后、关闭较慢、每个会话一个团队、不能嵌套、lead 固定；文件冲突靠分配不同文件，没有自动隔离。

**Codex**（https://github.com/openai/codex）：

- `multi_agent_v2`：`send_message` 只入队，不触发目标开始新一轮；`followup_task` 会触发目标新一轮；另有 `list_agents` 和 `interrupt_agent`；
- 共享工作目录，只靠提示词约定不要影响他人工作；
- `agent_message_board`（共享讨论板）是实验性功能，默认关闭。

**Anthropic 多 Agent 研究系统**（https://www.anthropic.com/engineering/multi-agent-research-system）：

- 多 Agent 比单 Agent 约多消耗 15 倍 token；
- 常见失败：过度派生、任务含糊导致重复劳动、更新过多、该停不停；
- 编码任务可并行的部分比研究任务少。

### Claude Workflow（本版参考）

来源是两篇社区文档（[alexop.dev](https://alexop.dev/posts/claude-code-workflows-deterministic-orchestration/)、[claude-code-ultimate-guide](https://github.com/FlorianBruniaux/claude-code-ultimate-guide/blob/main/guide/workflows/dynamic-workflows.md)），不是官方原文，内容与 Claude Code 中 Workflow 工具的说明一致：

- 工作流是一个 JS 脚本，控制流（循环、分支、扇出）在脚本里；每次 `agent()` 起一个全新上下文的子 Agent，只靠提示词传信息；
- `parallel()` 是屏障，等一批全部完成；`pipeline()` 没有屏障，每个条目各自走完所有阶段；
- 步骤间靠脚本变量和带 schema 校验的结构化输出交接，不是 Agent 之间发消息，中间结果不进主对话；
- 并发有上限，超出排队；有总 token 预算和 `agent()` 调用总数上限；
- 运行中不能向用户提问，只有权限审批会暂停；每次 `agent()` 调用有日志，可以恢复，所以脚本必须是确定性的；
- 默认共享工作目录，只有并行写同一批文件会冲突时才用 worktree 隔离；
- `/workflows` 按阶段显示进度，可以查看每个 Agent 的提示词和结果。

**与本版的取舍：** Claude 由脚本编排，中间结果不进主对话；本版由主 Agent 逐步规划，每步报告都进入主 Agent 上下文。好处是主 Agent 能看着结果调整下一步，代价是长工作流更占上下文，依靠 v0.10 的上下文压缩兜底。

## 与现有架构的关系

- `Conversation` 同一时刻只支持一次 `Run`，每个子 Agent 各自一个独立的 `Conversation`（v0.12 已是这种形态）；
- 步骤屏障和大纲状态放在运行时（`internal/subagent` 之上），不依赖主 Agent 的记忆；
- 主 Agent 的收件箱按“文本 + 来源”工作，步骤报告作为一条条目进入，沿用注入与唤醒路径；
- 审批已有先进先出队列和来源标注，最多 5 个任务同时请求审批时直接复用；
- 工具调用串行执行不变，步骤报告只能在两次模型请求之间被主 Agent 看到。

## 技术方案（已确认）

2026-10-28 确认。思路是不另起炉灶：在 v0.12 的后台子任务上加一本“进度账本”和一个 `workflow` 工具。子任务的运行方式、读写权限、文件范围、审批和日志都沿用 v0.12。

### 工具 `workflow`

一个工具，三种 `action`：

| action | 调用时机 | 参数 | 做什么 |
| --- | --- | --- | --- |
| `start` | 主 Agent 开始时 | 工作流标题；步骤列表，每步有标题和目标，最多 10 步 | 登记大纲，界面显示进度 |
| `run` | 轮到某一步时 | 步骤序号；任务列表，每个任务有描述、提示词、`kind`、`access`、`paths`，最多 8 个 | 整批校验，通过则全部启动，立即返回 |
| `end` | 主 Agent 想提前结束时 | 原因 | 取消运行中的任务，剩余步骤标为未执行 |

`workflow` 只在 TUI 入口注册，工具总数从 8 个变成 9 个。子 Agent 没有这个工具，`fork` 子任务也不能用（与 `task` 一样在执行时拒绝）。只读模式下仍然拒绝写入类任务。

### 一次运行的流程

1. 主 Agent 调用 `start`，运行时把大纲记进账本，界面显示全部步骤。
2. 主 Agent 调用 `run` 启动第 1 步。运行时先整批检查：步骤序号对不对、任务数有没有超限、参数是否有效、文件范围是否重叠或与运行中的任务冲突。任何一项不通过，整批退回，不启动任何任务。
3. 检查通过后，这一步的所有任务一次登记，能跑的先跑，其余排队。主 Agent 不等待。
4. 这一步的任务全部结束时，运行时把所有报告和账本里的进度拼成一条消息，放进主 Agent 的收件箱。主 Agent 正在运行就在下一次请求前注入，空闲就被唤醒，与 v0.12 相同。
5. 主 Agent 读完报告，调用 `run` 启动下一步。最后一步结束后，工作流自动收尾。

### 各个环节怎么处理

- **并行与排队。** 同时运行的名额是一个共用的池子，上限 5 个，`task` 和工作流的任务都占用。工作流的任务排队等名额；`task` 没有名额时仍然直接被拒绝，与 v0.12 一致。
- **文件范围。** 启动一步时，整批任务的范围一次登记，包括还在排队的任务；一步内范围重叠则整批拒绝。每个任务结束时各自释放。
- **`fork` 的快照。** 只有主 Agent 在执行工具的那一刻才能安全读取它的上下文，所以 `fork` 任务的快照在 `run` 调用时就取好，排队的任务也一样，之后才按名额启动。`fork` 在一步里不限制数量，提示词提醒批量并行时优先用 `fresh`。
- **步骤报告。** 一步的报告总量（含运行时进度块、每份报告的头部、数据声明和截断说明）不超过 32 KiB：先扣掉固定开销和每份报告约 640 字节的包装，再按任务数平分给正文，例如 8 个任务时每份约 3 KiB；子 Agent 的提示里同时要求写精简的结论。整步报告作为收件箱里的一个条目整体送达，不会被 v0.12 的 24 KiB 合并上限拆开。报告沿用“仅作数据”的声明。
- **运行时块在前。** 整步消息的第一部分是运行时生成的步骤标题和工作流进度（含下一步），之后是一条分隔行和各任务的报告。报告正文里以 `[子任务 `、`[工作流进度`、`[以上是子任务输出`、`下一步：` 等开头的行在嵌入前会被转义，正文无法伪造进度块或数据声明。
- **唤醒。** 普通子任务结果的唤醒仍受“连续唤醒 5 次”的保险阀限制；步骤结束的唤醒单独计数，上限 20 次（一个工作流最多 10 步，留出两倍余量）。两类计数都在用户输入时归零，连续起新工作流或反复派发最终也会撞上上限。用户正在输入时不抢占，报告留到下一次请求。
- **失败。** 失败、超时、达到上限的任务照常写进报告，步骤照常结束，由主 Agent 决定下一步。
- **取消与退出。** `Ctrl+C` 取消运行中的任务、丢弃排队的任务、剩余步骤标为未执行，不产生报告。之后主 Agent 再调用 `run` 会得到“工作流已被取消”的提示，由它去问用户。`/exit` 的行为与 v0.12 一致。`end` 的效果与取消相同，只是由主 Agent 发起：它会等被取消的任务真正释放文件范围和并发名额（最多 10 秒）再返回，主 Agent 紧接着重新开始时不会撞上刚被取消的占用；`Ctrl+C` 在界面事件循环上执行，不能等待，只取消不等待。
- **顺序与唯一性。** 步骤必须按序号顺序启动，不能重复启动，上一步没结束不能启动下一步；同一时间只有一个进行中的工作流。
- **记忆审查。** 步骤报告是注入的消息，沿用 v0.12 的排除规则，不会成为自动记忆的依据。

### 界面实现

- 工作流每次状态变化（登记、步骤启动、任务状态变化、步骤结束、收尾），运行时把整个工作流的当前状态发给界面，界面保存最新状态并照着画，不逐条处理增量。
- 空闲布局：任务区放在输入框下边线和页脚之间；输入框光标位置不再加上任务区的行数。忙碌布局沿用 v0.12 的位置。
- 工作流内的任务结束时不单独打印提示；每步结束和整个工作流结束时各打印一行汇总。单个子任务的结束提示保持 v0.12 的行为。
- 高度上限、折叠优先级和窄终端降级见“界面”。

### 日志

主会话 JSONL 增加 `workflow_start`（标题和大纲）、`workflow_step_start`、`workflow_step_end`（步骤序号、任务数、各状态数量）和 `workflow_end`（`completed`、`ended_early`、`canceled`）。子会话的元数据增加所属的步骤序号。每个任务仍有自己的 `subagent_start`/`subagent_end`。事件名是暂定的，以实现为准。

### 提示词

主 Agent 的委派指引增加 `workflow` 的用法：什么情况下用（任务能分成前后依赖的几步，每步内有可并行的部分），什么情况下用 `task` 或直接做；先声明大纲，轮到某一步再给细节；不要空等；并行任务不要写同一批文件；批量并行优先用 `fresh`；步骤不要拆得太碎。子 Agent 在工作流里运行时，提示里增加报告长度的要求。

### 验收场景

每个场景都要有自动化测试覆盖，其中涉及界面和整体流程的用 PTY 终端模拟：

1. **大纲登记。** `start` 后界面显示全部步骤和标题；步骤数超过 10、缺少标题、已有进行中的工作流，都被拒绝。
2. **逐步并行。** `run` 启动一步，多个任务并行，主 Agent 不等待，可以结束本轮。
3. **步骤屏障。** 一步内的任务陆续结束时主 Agent 不被打扰；最后一个结束时，所有报告合并成一条送回，只唤醒一次，并附带工作流进度。
4. **排队。** 一步 8 个任务时同时只有 5 个在跑，其余随空出的名额自动启动。
5. **整批拒绝。** 超过 8 个、范围重叠、与运行中任务的范围冲突、参数错误时，没有任何任务被启动。
6. **顺序约束。** 跳步、重复启动、上一步没结束就启动下一步，都被退回并说明原因。
7. **失败不终止。** 一步里有任务失败或超时，整步照常送回并带失败信息，工作流可以继续。
8. **提前结束。** `end` 后运行中的任务被取消，剩余步骤标为未执行。
9. **取消。** `Ctrl+C` 取消运行中的任务、丢弃排队的任务、不唤醒主 Agent；之后 `run` 被拒绝并提示工作流已取消。
10. **保险阀。** 10 步的工作流不会被“连续唤醒 5 次”拦住（步骤唤醒单独计数、上限 20）；非工作流的唤醒仍然受限；连续起新工作流最终也会被拦住。
11. **用户输入时不抢占。** 用户正在输入时步骤报告留在收件箱，下一次请求一起送到。
12. **与 `task` 共用名额。** 名额用完时 `task` 被拒绝，名额空出后可以再派。
13. **权限。** 只读模式拒绝写入类任务；`default` 模式下多个任务同时请求审批，面板标明来源并先进先出。
14. **报告体量。** 8 份报告加进度的总量不超过上限，被截断的报告带说明，数据声明保留。
15. **界面。** 空闲和忙碌两种布局；高度上限、折叠优先级、窄终端的一行摘要；任务结束的打印规则。
16. **日志。** 主会话和子会话记录里有工作流、步骤及其关联。
17. **工具数量。** TUI 入口 9 个工具；非 TUI 入口不注册 `workflow`；子 Agent 和 `fork` 子任务不能使用它。
18. **记忆边界。** 步骤报告不进入自动记忆审查。
19. **v0.12 回归。** v0.12 的 19 个验收场景仍然通过，界面相关的断言按新布局调整。

### 与方案的差异

- **保险阀不是完全豁免。** 原方案说“步骤唤醒不计入保险阀”。复核发现：只要界面显示着工作流，所有唤醒都不计数，连续起新工作流的循环永远不受限。现在保留单独的步骤唤醒计数（上限 20），普通唤醒仍是 5 次，两类计数都在用户输入时归零。
- **报告总量按整条消息计。** 原写法只约束报告正文，8 份报告加上进度和每份的头尾实际约 34–38 KiB。现在先扣掉固定开销和每份约 640 字节的包装，再平分正文；最坏情况下（最长标题、最长描述、每份 40 KiB 正文）整条消息也测试断言不超过 32 KiB。
- **运行时块前置并转义正文标记。** 报告正文可能原样抄回仓库里的文本，伪造 `[工作流进度]` 和“下一步”。现在进度放在消息最前面，正文里同形的块标记和“下一步：”“所有 …”开头的行在嵌入前被转义。
- **`end` 等待范围释放。** 原方案只说“取消”。复核发现批量工具调用里 `end` 紧接着 `run` 同一批路径时，会撞上刚被取消任务的占用。现在 `end` 等它们真正释放文件范围和名额（最多 10 秒）；`Ctrl+C` 在界面事件循环上执行，仍然只取消不等待。
- **退出时同步交付工作流结束事件。** `CancelAll` 的异步事件可能晚于日志关闭，导致 `workflow_end` 记录丢失并打印误导性警告。`Close` 路径改为同步交付，日志关闭后不再重建会话文件。
- **路径拒绝控制字符。** `paths` 会原样进入子 Agent 的系统提示，含换行的路径可以伪造出一整行规则；现在在 `task` 和 `workflow` 共用的参数解析里拒绝控制字符。
- **批内范围冲突的提示措辞。** 同批任务互相重叠时，错误信息不再点名刚被回滚、永远不会结束的子任务，而是指出是哪两个任务、哪对路径重叠。
- **任务行截断保留状态。** 标题很长或终端很窄时先截断标题，行尾的“3/5 个任务完成”“等待审批”不被挤掉。
- **审批面板的 `Ctrl+C` 提示**把工作流算进去：忙碌且工作流进行时显示“取消本轮和整个工作流”。
- **报告截断函数支持按任务调整上限**，单个委派的任务仍是 8 KiB。

## 风险与限制

1. **上下文占用。** 每步的报告都进入主 Agent 上下文，长工作流更占上下文，依靠 v0.10 的上下文压缩兜底。
2. **成本。** 多个子 Agent 并行，token 消耗随任务数线性增长；`fork` 还要带着主对话历史。上限只是起始值，等真实模型观察后调整。
3. **文件范围对 `bash` 无效。** 与 v0.12 相同，是防误写的护栏，不是安全边界。
4. **计划不能中途修改。** 方向错了只能提前结束再另起一个，已经完成的步骤不会复用。
5. **不持久化、不可恢复。** 进程退出后工作流丢失，与 v0.12 一致。
6. **运行时只校验形式。** 大纲和任务是否合理取决于模型，运行时只检查数量、顺序、范围和参数。
7. **排队的 `fork` 用的是派出时的快照。** 它启动得晚，但看到的仍是 `run` 调用那一刻的对话。

## 默认设定

以下是方案讨论中替用户定的小决定，用户已同意：5 个并发的名额同时作用于 `task`；`fork` 在一步里不限制数量；一步的报告总量取 32 KiB。

## 与权限收口的关系

Workflow 的成员之间不通信，所以 Agent Team 才有的“Agent 消息能否代表用户同意”“成员之间转授权限”两类新问题不会出现。仍然新增的权限场景是：最多 5 个任务同时请求审批。因此 v0.7 权限模型的验收与最终收口仍安排在 v0.13 之后一并处理。2026-10-29 已确认收口方案（命令分两档、统一分段器、本会话内允许，会话授权对 workflow 任务同样生效、队列里同键审批自动放行），见 [v0.7](v0.7.md)。
