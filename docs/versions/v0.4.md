# v0.4 · 工具系统

**状态：讨论中。本文是初步方案草案，尚未开始实现。**

[返回总体路线图](../johnny-code-roadmap.md)

## 本版目标

在 v0.3 统一模型接口的基础上，建立 Johnny-Code 自己的工具系统，让模型可以请求受控工具，并让程序完成工具定义、注册、参数校验和执行，再将结构化结果交回调用方。

本版的直接成果是一个可以独立测试的工具运行层。它可以被 v0.5 Agent Loop 调用，但本版不负责根据工具结果自动再次请求模型。

## 与前后版本的边界

### 复用 v0.3

- 复用 `model.ToolDefinition` 作为发送给模型的工具定义基础。
- 复用 `model.ToolCall`、`model.ToolResult` 和工具消息，保持不同模型协议下的调用 ID 关联。
- 复用 `model.Request.Tools`，由 Agent Loop 在每次模型请求中传入当前可用工具。
- 复用 v0.3 的统一错误、取消和上下文传递约定。

### v0.4 负责

- 工具实现的统一接口。
- 工具注册表和名称查找。
- JSON 参数解析与工具级校验。
- Bash 命令执行、文件读取、精确编辑和文件写入四类基础工具。
- 工作目录、路径边界、命令执行目录、超时和结果错误的明确规则。
- 单个工具的执行结果结构，以及对 v0.3 `ToolResult` 的转换。

### 后续版本负责

- **v0.5：** 根据 `tool_call` 调用工具、把结果放入下一轮消息、判断继续或结束，形成 Agent Loop。
- **v0.6：** 在 TUI 中显示工具状态、参数、结果和取消操作。
- **v0.7：** 从 Skills 中加载工具相关任务指导。
- **v0.8：** 接入 MCP 提供的外部工具。
- **v0.9：** 统一治理工具输出大小、上下文预算、历史压缩和资源消耗。

v0.4 不执行模型返回的工具调用循环，也不引入 MCP、Skills、SubAgent 或长期记忆。

## 初步架构

```text
Agent Loop / 测试调用方
        ↓ ToolCall
工具注册表 Registry
        ↓ 按名称查找
工具定义 Definition + 执行器 Executor
        ↓
Bash / 读取 / 编辑 / 写入
        ↓ ToolResult
统一模型消息层
```

建议把工具系统放在独立的 `internal/tool` 包中。模型层只负责工具定义的协议转换；工具层不依赖 Anthropic 或 OpenAI SDK。

## 统一工具接口草案

建议工具本身只关心定义和执行：

```go
type Tool interface {
    Definition() model.ToolDefinition
    Execute(context.Context, json.RawMessage) (Result, error)
}

type Result struct {
    Content string
    IsError bool
}
```

执行上下文需要携带本次工具运行的边界信息，而不是让每个工具自行读取全局配置。可在实现时使用显式的 `Runtime` 或构造参数提供：

- 工作目录。
- 文件系统访问根目录。
- 命令执行环境和命令工作目录。
- 单次执行超时。
- 输出大小上限的基础值。
- 取消信号。

具体是否将这些字段放入 `context.Context`，还是使用工具运行时结构体，需要在实现前确定。倾向于用显式结构体表达资源边界，`context.Context` 只负责取消和截止时间。

工具结果需要区分三种情况：

1. 参数或工具名称无效，工具没有开始执行。
2. 工具已执行但目标操作失败，例如文件不存在或命令返回非零状态。
3. 工具成功完成并产生结果。

前两类都可以转换为 `model.ToolResult{IsError: true}`，但内部错误类型和用户可见文本要保留差异。原始错误不应自动回显凭据、环境变量或完整命令环境。

## 注册表草案

```go
type Registry struct {
    // 内部按工具名保存唯一实例。
}

func (r *Registry) Register(Tool) error
func (r *Registry) Get(string) (Tool, bool)
func (r *Registry) Definitions() []model.ToolDefinition
func (r *Registry) Execute(context.Context, model.ToolCall) (Result, error)
```

注册规则初步建议：

- 工具名称不能为空，只允许稳定的 ASCII 标识符。
- 重复名称直接报错，不静默覆盖已有工具。
- `Definition()` 返回的名称必须与注册名称一致。
- 输入 schema 必须是合法 JSON 对象，并与 v0.3 发给模型的定义一致。
- `Definitions()` 返回稳定排序，避免请求内容因 map 遍历顺序变化。
- `Execute()` 只执行已注册工具；未知工具返回结构化错误结果，不 panic。
- 注册表本身不自动执行工具，也不创建新的模型请求。

是否允许注册表在运行中追加或删除工具需要讨论。初步倾向于构造阶段完成注册，运行期间只读；这样 v0.5 Agent Loop 可以在一次调用中稳定地看到工具集合。

## 第一批内置工具

参考 Claude Code 的基础工具形态，建议本版固定为四个工具：

| 工具 | 作用 | 初步输入 |
| --- | --- | --- |
| `bash` | 在工作目录执行命令，也可通过 `grep`、`find` 等完成搜索 | `command`、可选超时 |
| `read` | 读取工作区内的文本文件 | `path`、可选行范围 |
| `edit` | 对已有文件进行精确修改 | `path`、旧文本、新文本、可选替换策略 |
| `write` | 创建或整体写入文件 | `path`、`content` |

搜索不单独提供 `search_files` 工具，由 `bash` 承担。这样工具数量更少，模型需要学习的契约更简单，也与目标产品的基础工具形态保持一致。代价是搜索输出和命令安全边界由 Bash 工具统一处理，需要更明确的超时、输出和确认策略。

工具的具体 JSON schema、输出格式和是否支持二进制文件需要结合实现复杂度确定。第一版优先支持文本文件，遇到二进制或无法按 UTF-8 读取的内容返回清晰错误。

### `bash`

- 命令在明确的工作目录中启动，默认不改变 Johnny 进程的工作目录。
- 可以执行构建、测试、版本控制和搜索命令；工具本身不把搜索另建为特殊 API。
- 继承的环境变量需要经过筛选，不能把 API Key 等敏感配置无条件传给命令。
- 捕获 stdout、stderr、退出码和取消状态。
- 设置默认超时和输出上限；达到上限时停止或截断的行为需要确定。
- 是否每次执行前要求人工确认，是本版必须讨论的安全边界。v0.6 有 TUI 前，不能依赖尚未存在的交互界面。

### `read`

- 解析相对路径并限制在工作区根目录内。
- 拒绝路径穿越、工作区外绝对路径和无法确认边界的符号链接。
- 返回文件内容以及必要的行号信息，是否默认加行号待确认。
- 目录、特殊文件、超出单次读取限制的文件返回错误。

### `edit`

- 编辑前再次确认目标路径在工作区内。
- 优先使用带上下文的精确替换，避免模糊覆盖整个文件。
- 对目标不存在、匹配次数不符合预期、内容冲突和写入失败分别报错。
- 写入采用临时文件和替换，是否保留原文件权限需要实现时确定。
- 不创建目标不存在的文件；创建新文件统一使用 `write`。

### `write`

- 解析相对路径并限制在工作区根目录内。
- 负责创建新文件，也可以按明确规则整体覆盖已有文件。
- 父目录不存在时是否自动创建需要确认；初步倾向于不自动创建任意目录。
- 写入采用临时文件和替换，避免进程中断留下半个文件。
- 覆盖已有文件是否需要确认，与 Bash 的命令确认策略一起确定。
- 不执行 `content` 中的命令或表达式，内容只作为文件字节写入。

## 路径与执行安全

工具系统直接触碰文件和命令，边界需要在接口层明确：

- 工作区根目录是显式传入的绝对路径，不从工具参数推断。
- 文件工具默认只允许工作区内的路径；`..`、绝对路径、符号链接和挂载点的处理需要统一规则。
- 命令工具默认在工作区根目录运行，但命令本身可能访问其他目录；是否提供沙箱或允许列表不在本版假设中，应先明确当前安全级别。
- 工具不能读取 `.env` 并把凭据作为结果返回；输出错误需要避免携带敏感环境信息。
- 所有工具都响应 `context.Context` 取消，避免取消后继续写文件或运行命令。
- 错误要返回可识别的类型和稳定的用户提示，不能 panic。

## 待讨论的关键决策

1. 工具接口中工作区、输出上限和命令环境采用怎样的显式运行时结构。
2. 四个内置工具是否一次全部实现，以及 `bash` 是否承担搜索命令。
3. `edit` 采用精确文本替换、行级编辑，还是抽象为多种明确操作。
4. `write` 是否允许覆盖已有文件、是否自动创建父目录。
5. `bash` 的人工确认策略、环境变量继承策略、超时和输出限制。
6. 工作区内符号链接、隐藏目录、`.git` 和 `.env` 的统一处理规则。
7. 工具错误如何转换为模型可见的 `ToolResult`，以及内部错误向 CLI 暴露到什么程度。
8. 本版是否提供一个仅用于测试和后续 Agent Loop 的 `Registry.Execute` 入口，暂不接入 CLI 主流程。

## 候选验收标准

- 可以注册四个基础工具，重复名称和非法定义被拒绝。
- `Definitions()` 返回稳定、完整且能直接交给 v0.3 `Request.Tools` 的工具定义。
- 根据合法 `ToolCall` 能找到正确工具并执行，结果包含调用 ID、正文和错误状态。
- 根据未知工具名、非法 JSON 参数和不符合 schema 的参数返回结构化错误，不 panic。
- `read`、`edit`、`write` 不能访问工作区外路径。
- `edit` 在匹配失败或匹配次数不符合预期时不改动目标文件。
- `write` 能正确创建文件，并按确认后的规则处理覆盖和父目录。
- `bash` 正确返回 stdout、stderr、退出码、取消和超时结果，并遵守工作目录及输出边界。
- Bash、文件读取、编辑和写入都能响应取消。
- 工具执行失败不会修改不相关文件，不泄露 Key 或完整敏感环境。
- 使用临时工作区的自动化测试覆盖正常、非法输入、路径越界、失败、取消和超时场景。
- v0.3 的模型适配器仍可以接收工具定义和工具结果消息；本版不要求 CLI 自动循环调用模型。

## 初步实现顺序

1. 确认工具运行时边界和命令执行确认策略。
2. 定义 `internal/tool` 的接口、结果、错误和运行时结构。
3. 实现注册表、定义校验和调用分发。
4. 实现 `read`，建立路径和输出限制基础。
5. 实现 `edit`，补充精确修改和失败不落盘验证。
6. 实现 `write`，补充创建、覆盖和失败不落盘验证。
7. 实现 `bash`，补充取消、超时、环境和输出边界验证。
8. 与 v0.3 的 `ToolDefinition`、`ToolCall`、`ToolResult` 做转换测试。
9. 验证工具层独立可运行，再决定是否为 v0.5 Agent Loop 提供调用入口。
