# Johnny-Code 迭代路线图

目标是使用 **Go** 逐步构建一个以终端为入口的 Coding Agent。每个版本形成一个可以运行、可以解释、可以验收的成果，让使用体验与对项目的理解一起增长。

本文记录总体方向、版本顺序和协作方式。各版本的具体讨论、技术方案、决策与验收记录保存在 `docs/versions/` 下，每个版本一个文档。

版本号用于表达建设顺序；后续可以根据讨论和验收结果调整范围或继续拆分。

| --- | --- | --- | --- |
| v0.1 | 模型调用 | 在终端输入一段话，获得真实模型回复，并能理解调用失败的原因。 | [初步验收通过](versions/v0.1.md) |
| v0.2 | 全局 CLI 入口 | 安装后在任意目录输入 `johnny` 启动程序，默认使用当前工作目录。 | [验收通过](versions/v0.2.md) |

| v0.5 | Agent Loop | 根据工具结果推进多步任务，支持同进程多轮上下文、单任务入口、取消和仅用于排查的会话记录。 | [联合验收通过](versions/v0.5.md) |
| v0.6 | TUI | 通过简洁的终端界面进行对话、查看执行状态和结果，并输入或中断任务。 | [验收通过](versions/v0.6.md) |

| v0.10 | 上下文治理 | 管理用量、预算、按需加载、工具输出与历史压缩，验证长任务体验和资源使用效果。 | [已确认冻结](versions/v0.10.md) |

## 文档组织约定

- **总体路线图：** 维护项目目标、版本顺序、大体范围、跨版本原则及版本文档索引。
- **版本讨论文档：** 统一放在 `docs/versions/v0.x.md`，随该版本讨论持续更新。
- **内容组织：** 版本文档区分目标、已确认事项、方案草案、待讨论问题、验收标准与实际记录。
- **按需建立：** 开始讨论某一版时再创建对应文档；已有初步讨论可以先记录，并标明状态。
- **记录状态：** 明确区分讨论、实现和验收进展，避免将方案建议写成已确认或已完成事项。

## 贯穿各版本的建设方式

- **TUI 独立引入并持续演进。** v0.6 完成基础界面，后续每版补充与新能力对应的必要交互和状态。
- **模型接口独立建设并持续验证。** v0.3 建立统一入口，随着工具、上下文和其他供应商接入需求完善适配，并保留模型服务的能力差异。
- **全局入口保持一致。** v0.2 建立 `johnny` 命令，后续版本沿用同一启动方式。
- **会话记录与长期记忆分别演进。** 基础 Agent 阶段保留任务过程与对话；v0.11 解决值得跨会话保存的信息及其维护方式。
- **先完成能力，再建设权限体系。** v0.4 和 v0.5 采用面向开发推进的直接执行模式，不加入人工确认或权限拦截；仍处理取消、超时和输出限制等执行生命周期问题。v0.7 在 TUI 基础上统一权限策略、交互确认、凭据环境隔离和执行审计，并明确应用层策略不等同于 OS sandbox。Skills 已在 v0.8 接入；MCP 在完成设计调研后暂缓，后续有明确外部服务需求时再评估，不阻塞上下文治理、长期记忆和 SubAgent。2026-10-25 起，开发阶段 CLI 默认进入 `allow`，权限模型验收与收口后置；先集中完成上下文治理、长期记忆和 SubAgent。操作系统隔离是否纳入后续版本另行决定。具体机制在对应版本讨论。
- **可靠性跟随功能交付。** 每个版本处理自身引入的配置错误、执行失败、中断和必要验证。

## 每个版本的协作节奏

1. **讨论当前版本：** 明确问题、范围与验收场景，解释核心机制，将讨论记录到对应版本文档。
2. **实现并运行：** 完成当前能力，使用真实场景观察行为。
3. **一起验收：** 检查正常路径和关键失败场景，修正发现的问题。
4. **保留理解材料：** 在版本文档中记录最终方案、关键取舍、执行流程、验收结果与当前限制。
5. **再进入下一版：** 根据本版实际结果调整下一版范围。
