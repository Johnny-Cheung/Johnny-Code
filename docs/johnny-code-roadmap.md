# Johnny-Code 迭代路线图

目标是使用 **Go** 逐步构建一个以终端为入口的 Coding Agent。每个版本形成一个可以运行、可以解释、可以验收的成果，让使用体验与对项目的理解一起增长。

本文记录总体方向、版本顺序和协作方式。各版本的具体讨论、技术方案、决策与验收记录保存在 `docs/versions/` 下，每个版本一个文档。

版本号用于表达建设顺序；后续可以根据讨论和验收结果调整范围或继续拆分。

## 文档组织约定

- **总体路线图：** 维护项目目标、版本顺序、大体范围、跨版本原则及版本文档索引。
- **版本讨论文档：** 统一放在 `docs/versions/v0.x.md`，随该版本讨论持续更新。
- **内容组织：** 版本文档区分目标、已确认事项、方案草案、待讨论问题、验收标准与实际记录。
- **按需建立：** 开始讨论某一版时再创建对应文档；已有初步讨论可以先记录，并标明状态。
- **记录状态：** 明确区分讨论、实现和验收进展，避免将方案建议写成已确认或已完成事项。

## 贯穿各版本的建设方式

- **TUI 独立引入并持续演进。** v0.6 完成基础界面，后续每版补充与新能力对应的必要交互和状态。
- **模型接口独立建设并持续验证。** v0.3 建立统一入口，随着工具、上下文和其他供应商接入需求完善适配，并保留模型服务的能力差异。
- **全局入口保持一致。** v0.2 建立 `johnny` 命令，后续版本沿用同一启动方式。
- **会话记录与长期记忆分别演进。** 基础 Agent 阶段保留任务过程与对话；v0.10 解决值得跨会话保存的信息及其维护方式。
- **可靠性跟随功能交付。** 每个版本处理自身引入的配置错误、执行失败、中断和必要验证。

## 每个版本的协作节奏

1. **讨论当前版本：** 明确问题、范围与验收场景，解释核心机制，将讨论记录到对应版本文档。
2. **实现并运行：** 完成当前能力，使用真实场景观察行为。
3. **一起验收：** 检查正常路径和关键失败场景，修正发现的问题。
4. **保留理解材料：** 在版本文档中记录最终方案、关键取舍、执行流程、验收结果与当前限制。
5. **再进入下一版：** 根据本版实际结果调整下一版范围。
